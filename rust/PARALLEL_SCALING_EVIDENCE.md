# BPE 训练的 CPU 多核扩展证据

本文只把“同一训练器、改变线程数”的结果作为强扩展证据。不同训练器之间的速度比，或 Python 版本到 Rust 版本的加速，都不等于线程扩展。固定模型的编码性能单独列出，不当作训练加速。

## 最直接的训练曲线：YouTokenToMe

[YouTokenToMe 官方 benchmark](https://raw.githubusercontent.com/VKCOM/YouTokenToMe/master/benchmark.md)测量同一个 BPE 训练器在 1、2、4、8、16 线程设置下的用时：输入是英、俄、中、日 Wikipedia 文本各自的前 1 GB，目标词表大小为 30,000。机器为 36 核 Xeon Platinum 8124M（3 GHz）、关闭超线程、256 GB 内存。下表中的加速比是用其原始秒数计算的，不是相对其他库的速度比。

| 语料 | 1 / 4 / 8 / 16 线程用时（秒） | 1→4 | 1→8 | 1→16 |
|---|---:|---:|---:|---:|
| 英语 | 62.1 / 25.2 / 20.6 / 19.8 | 2.46× | 3.01× | 3.14× |
| 俄语 | 58.1 / 25.9 / 20.5 / 21.8 | 2.24× | 2.83× | 2.67× |
| 中文 | 140.3 / 58.5 / 48.5 / 46.9 | 2.40× | 2.89× | 2.99× |
| 日语 | 187.5 / 75.3 / 57.7 / 62.8 | 2.49× | 3.25× | 2.98× |

项目称训练收益在 8 线程后不再明显，并在 README 中说明训练线程数会限制到 8。因而表里的 16 线程行应理解为 benchmark 报告的线程设置及其结果，不能据此断言实际使用了 16 个训练工作线程。该 benchmark 没有报告重复次数或方差；8 和 16 线程之间的小幅差异无法稳健判定。

这是 BPE 训练可利用多核的直接证据：这些输入上，4 线程约有 2.2–2.5×加速，8 线程约有 2.8–3.3×。它没有证明线程数增至几十核还能线性扩展。

输入结构也很关键。[YouTokenToMe README](https://raw.githubusercontent.com/VKCOM/YouTokenToMe/master/README.md)说明其 BPE 不会跨越单词边界合并，并将空格替换成边界标记。这使得训练可在独立单词上并行，并能按频次聚合相同词形。Wikipedia 是自然语言，但这种分解与把整个语料视为一个连续序列或单个巨型 piece 并不相同；公开曲线没有证明性能可直接迁移到这些场景。

## 其他结果及其边界

| 来源 | 测量或实现内容 | 对训练强扩展能说明什么 |
|---|---|---|
| [SentencePiece BPE trainer 源码](https://github.com/google/sentencepiece/blob/master/src/bpe_model_trainer.cc) | 当前实现先初始化 pair 频次，再在循环中依次从优先队列选出一个最高频 pair、应用合并并更新相邻 pair 的频次。 | 没找到同一训练器改变线程数的训练曲线。通用 `num_threads` 选项不能证明核心贪心 BPE 合并循环已并行。 |
| [SentencePiece 官方性能报告](https://google.github.io/sentencepiece/doc/performance_benchmark/) | 在 24 核 CPU 上，对固定的 Gemma 3 BPE 模型进行**编码**。数据为英、中、日、泰平衡语料，11.29 MB、60,720 行，测试 1–24 线程。吞吐从 1 线程的 7.44 MB/s 增至 4 线程的 23.03、8 线程的 36.66、24 线程的 52.43 MB/s。 | 说明对许多独立句子做编码可以扩展；这是推理，不是训练。输入是批量句子，不是连续字节流。 |
| [Batching BPE Tokenization Merges（BatchBPE）](https://arxiv.org/abs/2408.04653) | 用启发式上限将候选 pair 合并成批，以减少顺序处理工作。 | 论文没有 1/4/8/16 线程训练曲线。该上限可能改变 pair 的选择顺序和最终词表，因此批处理倍数不能作为精确贪心多核加速。 |
| [Faster Superword Tokenization](https://arxiv.org/html/2604.05192v1)（Schmidt、Tanner、Pinter；arXiv v1 日期 2026-04-06） | 报告在 1 GB 数据上，BoundlessBPE 从此前的 4.7 CPU 天降至 603 秒，SuperBPE 降至 593 秒。方法是按频次聚合候选 pretokens，并将 BoundlessBPE 改写为两阶段流程；论文称两阶段版本与原 BoundlessBPE 产生相同模型。详细训练表是 3 次平均值，并分别列预切分、合并和总时间。 | 这是减少算法工作量，不是线程扩展：作者明确说当前实现为单线程，未来可继续并行化。4.7 CPU 天与 603 秒的比较不是受控的线程数对照；论文没有给出该方法 1→N 线程曲线。它说明算法优化和多核并行可以互补。 |
| [YouTokenToMe benchmark 的竞品说明](https://raw.githubusercontent.com/VKCOM/YouTokenToMe/master/benchmark.md) | 作者在该 benchmark 中称 SentencePiece 的 BPE 训练不支持多线程，fastBPE 训练也不支持多线程。 | 这是该 benchmark 时期的说明，不是对当前实现的完整调查。对于当前 SentencePiece 贪心合并循环，源码更直接。 |

Faster Superword 论文还区分了精确的候选聚合/两阶段方法与可选的从左到右切分启发式。其报告的英语计算结果没有采用该可选启发式；作者指出启发式切分可能在后续高估候选频次并改变 pair 选择。解读“训练更快”时需要分清时间下降来自减少算法工作、改变训练语义、增加核心数，还是几者共同作用。

## 对高核数目标的启示

公开证据不支持“BPE 训练天然只能获得很小的多核收益”这一判断。YouTokenToMe 给出了同一训练器在自然语言上的线程曲线，在 8 线程前有实质收益。但目前找到的证据没有展示精确全局贪心训练扩展到 32 核，也没有证明以单个连续 piece 为单位的训练能达到相同扩展效果。这些仍是设计和测量问题。

本项目应继续把高核数扩展作为明确目标，同时区分并行域：独立预切分单元、互不冲突的 pair 出现位置，以及全局有序的 BPE 合并轮次，各自提供不同并行机会，也有不同的精确性约束。后续报告应在硬件允许时测同一实现的 1、4、8、16、32 工作线程；计入初始化与全部 BPE 合并轮次；同时报告吞吐和墙钟加速；并分别测自然语言预切分输入与单个连续输入。如果预处理或模型写出未计入计时，需单独报告。不要把这些线程加速比与另一库的速度比混为一谈。

BoundlessBPE 的 600×级改进尤其说明，减少顺序算法工作量可以让训练先变得可用，并与后续并行化叠加。它既不降低高核数目标的价值，也不能证明增加核心数可以替代低效的候选表示。

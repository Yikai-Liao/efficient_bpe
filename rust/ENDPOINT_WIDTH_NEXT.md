# 下一轮候选：并行语料端点的位宽

当前 owner 原型使用每位置一个 `AtomicU32`，频率和位置列表只保留一份。已有串行 CF16 不能直接等同于“ID 最多 65535”：`src/ablation/backends.rs` 的 `Halfword` 用半字数组和边界位图，在合并 token 的第二个物理槽保存 ID 的另一半。它能利用 token 已占据至少两个原始位置这一性质，且目前转换会新建 `Vec<u16>`，没有原地改 Vec 的分配布局。

一个较小、可独立验证的并行子问题，是在整轮 ID 上界可证明不超过 16 位时使用 `AtomicU16`。设初始长度表长度为 L、最多合并 R 次；若 checked 的 L+R≤65536，则任何新 ID 都在 0–65535 内。训练入口只分派一次到泛型的 16 位或 32 位端点内核，避免每次读端点都判断位宽。自动模式在不满足上界时选择 32 位；严格 16 位模式提前拒绝。仍用 `u32` 长度表，因此 token 长度超过 255 或 65535 本身不要求扩大端点 ID。这里限制的是词表 ID 域，不能宣传为无条件的 2 字节并行实现。

先用显式分配测量真实代价：原输入约 4N 字节，新端点约 2N 字节，转换瞬间可能同时占约 6N，实际还要看容量和 allocator 留存。稳态语料载荷减少不保证进程峰值按同样幅度下降。读取的工作集变小可能有利，写入时每缓存行容纳更多端点也可能增加伪共享；两者都要实测。规划完成后写入、写入完成后再规划的屏障，以及 AA 奇偶选择保持不变。

不要把 `Vec<u32>` 的指针直接包装成 `Vec<AtomicU16>`：即使调整容量使总字节数相等，两者的 allocator 对齐布局仍不相同。原地前向打包到原 `Vec<u32>` 的前半部、保持原类型析构，再借出原子半字视图，是更复杂的另一个设计。它需要正确字节序、原子别名和完整生命周期证明；`shrink_to_fit` 还可能重分配，既不保证没有转换峰值，也不保证降低 RSS。当前先不引入这个 unsafe 所有权方案。

更通用的半字 ID 拆分、边界位图并行更新也可研究，但那会改变端点解码和写入冲突证明，应作为后续独立算法。当前文档仅记录设计与限制，尚未实现或测量。

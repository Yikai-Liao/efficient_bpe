# Grouped occurrence patch: read-only invariant audit

Scope: `/tmp/efficient-bpe-grouped-plan/grouped.patch` against the Rust source copied on 2026-09-29. I read the patch, staged replacement files, public input validation, and archived serial trainer. I did not apply the patch, compile, or run tests or performance work during this audit.

## Finding

I found no ordering or `unsafe` counterexample introduced by grouping under the existing validated-input and historical-list invariants. The patch changes only how new occurrence records travel from each apply task to the coordinator; `select_plans`, corpus reads/writes, worker barriers, frequency-delta calculation, and global rule choice are unchanged. This is a conditional source-level conclusion, not dynamic verification.

## Why grouping preserves the observable trace

- Initial per-pair histories are appended by increasing physical position (`parallel_occurrence_snapshot.rs:489-503`). Every pair created later contains that round's fresh ID, so it receives all of its occurrence records during one rule only; subsequent rules can make those records stale but cannot add another occurrence of that same old pair.
- The coordinator's accepted plans are increasing by start position: worker validation checks each chunk and the boundary between chunks (`:237-270`, `:596-639`), then `select_plans` greedily removes overlapping `AA` candidates (`:84-130`). Apply tasks own contiguous plan-index ranges (`:665-683`). The coordinator receives results by worker index, not completion order (`:685-701`), and reduces them in that order (`:703-741`).
- Within a plan, the existing flat stream records the left edge at `before` and then the right edge at `pos`; `before <= pos`. A later disjoint plan's left boundary cannot be before the preceding selected plan's start. If the plans touch, `select_plans` sets `before` to the previous plan's start (`:108-110`); if they do not touch, the predecessor token starts after the previous plan's span. Thus records for any one pair remain nondecreasing across plans and worker chunks, including equal-position temporary edges. The grouped worker pushes to that pair's `Vec` in the same sequence (`:303-310`), and the reducer moves the first vector or appends later vectors (`:725-739`). HashMap iteration changes order *between different pair keys* only. Rule selection remains frequency plus packed-key lexicographic order, independent of fresh-key insertion order.
- `ABABAB`: consecutive `AB` matches are adjacent. The first creates temporary `(new,A)` at its start; the next removes it and creates `(new,new)` at that same start. If the matches are in different workers, their signed deltas are reduced by worker index, so the temporary pair exists before its removal. Grouping keeps its historical occurrence even if it is stale in a later rule. `AAAAA`: overlapping `AA` historical starts are skipped in left-to-right order; grouping only receives the accepted plans, while `stale_visits` counts the skipped ones. Neither case changes weighted self-pair frequency semantics.
- A weight belongs to the original piece containing a selected match start (`:120-126` or local `:391-392`). Matches cannot cross a zero separator, and a new left/right edge cannot cross one because a zero neighbor is omitted. Grouping does not alter the weight or the per-position pivot used when a new pair is selected later. Public validation bounds the total weighted adjacency by `u64` (`rust/src/trainer.rs:176-209`); a true pair frequency and each worker-chunk prefix state fit that bound. Signed `i128` deltas therefore have ample range, including `u64::MAX` as a single legal edge weight. `fresh` is checked only after all chunk deltas and occurrence vectors are reduced (`:742-753`).
- Stale historical positions remain in the same per-pair sequence. They are filtered by live token IDs and token lengths in the next validation (`:247-261`) or local scan (`:365-383`). Grouped vectors do not sort, deduplicate, or drop them.

## `unsafe` and phase ownership

The only unsafe operations in this path are private `get_unchecked` calls in `load`/`store` (`:37-60`), inherited without alteration by the patch. Public `parallel::train` validates corpus size `< 2^32`, dense IDs, sentinels, pivots, and maximum fresh ID before reaching this code. Initial scans use `1..last` and `pos+1 <= last`; a historical start is within the corpus. Validation checks `pos`, `right`, and `after <= last` before emitting a valid candidate (`:247-261`). `select_plans` rechecks its end, checks predecessor subtraction, and stores only accepted disjoint plans (`:84-130`). Apply computes the same boundaries and writes only `pos`, `right`, and possibly `after-1` (`:283-310`); adjacent plans occupy distinct indices, including when assigned to different workers. The local adaptive path checks its boundaries before loads/stores (`:358-406`). The Arc corpus length never changes. Atomic u32 accesses avoid data races, and all validation replies are received before any apply dispatch; all apply replies are received before global reduction or the next rule (`:616-701`). The grouped HashMap and Vec are worker-owned until sent through the channel, then coordinator-owned. No new shared mutable memory or unchecked index is added.

The strongest premise remains the existing endpoint representation: for a valid token start, `pos-1` identifies the previous token's right endpoint, and lengths/IDs at that endpoint lead to a valid predecessor start. The patch does not strengthen or weaken that premise. An erroneous future change to endpoint writes or validation could invalidate the unchecked proof, so checked/unchecked differential tests remain necessary.

## Limits and test targets

- This review does not establish performance. With mostly singleton fresh pairs, `HashMap<u64, Vec<u32>>` creates a table entry and a small Vec allocation per pair per worker; that can use more memory and CPU than a flat 16-byte record stream. `global_occurrence_entry_calls` counts coordinator pair-position lookups, not worker grouping cost or allocator traffic. The reducer still processes signed deltas serially and inserts fresh keys into the heap.
- The staged test covers long `AA` and `ABAB`, adaptive local and parallel rounds, both bounds modes, rules/final tokens/actual merges/visits/stales, and a `u64::MAX` single-edge case through the shared tests. On application, run those tests before benchmarking, then check RSS and worker-side time on high-uniqueness as well as repeated-pair data. An explicit assertion of historical-list nondecreasing order after grouped reduction would be useful as a debug-only test if a future implementation changes chunking.
- The patch was checked with `git apply --check` when staged. Because other agents may edit the live source before application, re-run that check and inspect any rebase conflicts. No live Rust file was changed for this audit.

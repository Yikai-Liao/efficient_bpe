# One-word scatter cache for dense AA bitmap

This independent crate clones the frozen `owned_aa_bitmap` trainer and changes only the bitmap scatter. The CLI keeps `--aa-order sort|bitmap-adaptive` (default sort), `--integer-hash std|ahash`, and `--heap-policy lazy|eager`. Within bitmap-adaptive mode, `--bitmap-scatter atomic|word-cache` (default atomic) selects the scatter kernel once per AA round. Sort never consults this flag. The `atomic` kernel remains the copied per-valid-position `fetch_or` control.

Each producer task in `word-cache` holds exactly one `(word_index, pending_bits)` accumulator on its stack. A valid historical AA start obtained from `inspect` adds its bit; a different word flushes the pending word through one atomic OR, and task end flushes the final pending word. A stale posting does nothing and does not force a flush. If positions revisit an earlier word, the task issues another OR for that word; this is correct because OR is associative, commutative, and idempotent. Different tasks can flush the same word concurrently through `AtomicU64::fetch_or(Relaxed)`. All tasks join before summary reads, so there is no new synchronization rule. The valid-edge count increments for every validated posting record, including duplicates; the later bitmap popcount equality check continues to reject duplicate valid starts even though the accumulator coalesces their bits.

`aa_bitmap_atomic_or_calls` counts actual fetch-OR operations in either kernel. `aa_bitmap_flush_calls` counts pending-word flushes in the cached kernel (zero in atomic control), and `aa_bitmap_scatter_tasks` counts historical posting chunks. Existing `aa_bitmap_valid_edges` and `aa_bitmap_scatter_seconds` show the work and elapsed phase. There is no new Vec, HashMap, corpus copy, or permanent index. The accumulator's worst case is one OR per valid edge when input positions alternate words, plus a comparison/branch per valid edge; it may therefore be slower. The full bitmap lifecycle, 64-word physical summary tasks, parity, routes, apply, density/capacity fallback, weighted frequency and owner commit remain unchanged from `owned_aa_bitmap`.

Tests compare both kernels to the serial full trace, and directly cover descending positions within one word, crossing and revisiting words, same-word producer tasks, a stale position inside a pending segment, duplicate valid posting rejection, and AA token length greater than 255 through the sort fallback. Performance claims require same-binary W1/W4 measurements, actual atomic-call counts, process HWM, and the best direct serial reference; reducing OR operations alone does not prove faster training.

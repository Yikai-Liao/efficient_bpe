# Adaptive cuts for globally ordered postings

This independent crate copies the frozen `owned_ordered_posting` trainer. It changes only non-AA region boundaries and the way a batch locates posting slices. `--cut-policy fixed` is the same-binary control; `adaptive` requires `--posting-order global --region-mode region --endpoint-plan tagged-fused --regions-per-worker 1`. Snapshot mode is rejected for adaptive cuts because its boundary descriptors belong to fixed cuts. If the 31-bit tagged-ID domain fails, the whole call uses the existing two-pass dynamic fallback and reports effective cut policy `fixed`.

Each selected posting is strictly increasing in physical position. After the previous batch has joined and committed, new cuts can therefore partition each posting with `partition_point`. Fixed and adaptive runs both build one `B × T` matrix of `(first,end)` ranges before region work; the planner reads it without further partition searches. AA continues to use the fixed physical cuts, including immediately after an adaptive non-AA batch. `T=min(workers,corpus.len())`; `T=1` builds only fixed ranges and records a single-region bypass. Empty or no-selected-batch calls need no candidate cuts.

For B selected rules, let H be their total historical posting length and Hmax the longest. If `H-Hmax ≤ H/(4T)`, the cheap candidate uses ranks `ceil(r Hmax/T)` of the longest posting, at `r=1..T-1`. Otherwise, if `H>4BT`, each posting supplies at most `4T` end-of-block samples, with block stride `ceil(Hj/(4T))` and actual block length as weight. Sort samples by position, add weights at equal coordinates, and choose the coordinate where cumulative weight first reaches `ceil(rH/T)`. Place cuts at position+1 and remove duplicates. Position fits `u32`, but total H, same-coordinate weight accumulation and CDF use checked `usize`; rank products use `u128`. A coordinate shared by different keys is counted once per key, including stale history. The bound on any nonempty candidate region's historical visits is less than `1.5H/T+B`, as derived in [the design note](../../../ADAPTIVE_ORDERED_CUTS_NEXT.md). This bounds posting reads, not valid merges, hashing or wall time.

Small work (`H≤4BT`) and any checked metadata-budget failure use fixed cuts. The 8 MiB value is a *candidate-selection guard* for additional metadata above the fixed range matrix; it estimates a second matrix, visit totals, cut headers and up to `4BT` `CutSample` elements at their actual Rust size (16 bytes here). The sample allocation's actual capacity and the built candidate's actual capacities are checked again. A candidate range allocation may briefly exceed that estimate before it is rejected, so this is not a hard allocation cap; allocator overhead and all other trainer structures are outside the proxy. We record separate peak sample, range and cut-header capacities. There is no O(N) marker or corpus copy. A cut can lie inside a long token; existing region endpoint and cross-region birth protocols remain responsible for correctness.

The coordinator calculates exact historical visits for fixed and candidate cuts from both range matrices and keeps the candidate only if its maximum per-region visits is strictly lower. Ties use fixed cuts. The two matrix constructions add `O(BT log Hmax)` binary searches; samples add at most `O(BT)` position reads and `O(BT log BT)` sorting. Their time and capacity are measured separately from region planning. `cut_region_count_min/max` record the selected non-AA region counts, which may be less than T after duplicate cuts. AA always uses T fixed regions. `region_count_effective` remains the initial fixed T for compatibility, so it must not be interpreted as every epoch's region count. `cut_fixed_max_visits_sum`, `cut_candidate_max_visits_sum`, and `cut_selected_max_visits_sum` sum per-batch maxima; candidate sum covers only batches that built one. The measured performance result must be judged with total `call_seconds` and actual valid merge distribution, because balancing stale reads alone need not reduce runtime.

The implementation has focused tests for dominant and sampled paths, duplicate cross-key positions, skewed halves, duplicate cut removal, single-region bypass, weighted/AA/long-token traces and tagged-domain fallback. The central full-trace oracle and benchmark are run by the shared executor against the frozen source.

# Dense AA bitmap experiment

This independent crate copies the frozen `owned_integer_hash` trainer and changes only its self-pair (`AA`) branch. `--aa-order sort` is the sort/valid-start/Plan control; `--aa-order bitmap-adaptive` uses the bitmap only when the selected historical posting has at least `ceil(corpus_positions/16)` records and the actual bitmap allocation fits within the selected posting's heap-capacity bytes. Allocation failure falls back to sort. The actual-capacity guard runs after allocation/zeroing, so an allocator that substantially overallocates can cause a short-lived transient peak before fallback; this is not a strict pre-allocation RSS limit. Both modes retain `--integer-hash std|ahash`, weighted frequencies, fresh IDs, and the same owner update.

The bitmap has one bit per physical corpus position, shared by all workers. It is filled only from the selected pair's historical posting: each candidate start passes `inspect` on the stable pre-update corpus before its bit is set with an atomic OR. This qualification is necessary because a long token stores its ID at both endpoints; a physical scan for adjacent ID values can mistake an endpoint tag for a token start. A popcount check rejects duplicate valid posting positions that a bitmap would otherwise coalesce. The selected posting is released after the scatter joins.

Consecutive set-bit positions differ by `len(A)` within an AA run. Each fixed 64-word physical chunk (4096 positions) computes the same first/last/trailing parity summary as `aa_parity`; the coordinator scans only chunk summaries. The first subsequent bit traversal selects the global left-to-right even-parity starts, re-inspects their neighbors on the stable snapshot, and routes deltas and birth chains. For a selected start `p`, `bit[p-len(A)]` proves that the immediately preceding selected match ends at `p`; `bit[p+2len(A)]` proves that the next selected match starts at `p+2len(A)`. These tests determine whether to suppress the shared left boundary and whether the right birth is `Z/Z`. All route jobs join before writes. A second selected-bit traversal writes only the geometric endpoints of disjoint chosen spans. The bitmap then drops before owner commit. No valid-position Vec or Plan Vec is created in bitmap mode.

The extra live allocation during scatter is `8*bitmap.capacity()` bytes beside the selected posting. After scatter, it coexists with `O(G)` chunk summaries and with the owner route outputs; it never has a per-worker corpus copy. `peak_aa_plan_capacity_bytes` reports actual summed Plan-Vec capacity in sort rounds and remains zero for an all-bitmap AA workload. It excludes the sort path's valid-start Vec capacity and Vec headers; process HWM remains the whole-call memory check. Existing `peak_plan_len` is a logical selected-position count, not allocated Plan memory. `aa_bitmap_peak_bytes` is the actual word-Vec capacity, not just its logical payload. `aa_bitmap_chunks`, `aa_bitmap_peak_chunks`, and `aa_bitmap_chunk_words` expose the physical task count; `aa_bitmap_init_seconds` includes allocation and zero initialization, even for a capacity-guard fallback. The density threshold gives `N/8 <= 2H+8` bitmap payload bytes for historical posting length `H`; the capacity guard also checks the allocation. Per selected AA key, scattering costs `O(H)` and the three word traversals cost `O(N/64+V)` each. Since a selected key cannot reappear, `sum H` is bounded by all retained historical posting records. Dense stale postings can still lose on constants, and contention on hot bitmap words remains possible.

The stable snapshot requirement is strict: route reads the corpus and computes weighted deltas entirely before the apply traversal starts. The apply traversal reads only immutable bitmap/parity metadata and writes nonoverlapping spans. `Relaxed` bitmap operations are sufficient because each stage joins before the next reads the bits. AA parity uses `u32` token lengths and checked adjacency arithmetic, including cross-chunk runs, empty chunks, and piece sentinels. The oracle gate must compare every rule's pair/frequency and final tokens for both modes at W1/W4 before any timing conclusion.

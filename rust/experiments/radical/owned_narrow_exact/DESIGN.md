# Isolating endpoint width from corpus allocation

`owned_narrow_exact` copies the frozen `owned_narrow` trainer and adds one CLI mode: `--corpus-width u32-exact`. The original `u32` default retains its consuming `Vec<u32> -> Vec<AtomicU32>` collection, which may reuse the input allocation. `u32-exact` allocates a new `Vec<AtomicU32>` with requested capacity equal to the input length, fills it while the input `Vec<u32>` remains alive, then drops the input. The existing `u16` and eligible `auto` paths likewise allocate and fill a new `Vec<AtomicU16>`. All modes share the same generic training kernel, owner index, posting layout, candidate selection, AA parity and grouped birth route. Only conversion allocation and endpoint width vary.

This supplies two same-binary contrasts. `u32` versus `u32-exact` holds width at 32 bits and changes the allocation lifecycle. `u32-exact` versus `u16` holds the explicit new-allocation lifecycle and changes width. If the full-call bound allows 16 bits, `auto` enters precisely the `u16` branch, with the same endpoint type and allocation; only its request label differs. An `n=1` timing difference between `auto` and `u16` therefore measures run noise, not a distinct algorithm.

Let `L = initial_lengths.len()` and `R = max_merges`. Shared validation checks initial IDs belong to the dense `0..L` domain. Fresh IDs begin at `L` and at most `R` rules are created, so checked `L + R <= 65536` proves every endpoint ID fits `u16`. Strict `u16` rejects a failed bound before pool/index creation; `auto` falls back to the inherited `u32` path. Initial values and `write_merge`'s zero/fresh ID stores use a debug assertion followed by a safe cast in the `u16` monomorphization; the release hot path does not repeat the proven check. Lengths and posting positions remain `u32`, including for tokens longer than 255.

The CLI reports actual `corpus_width`, requested width, and `corpus_allocation` (`consuming-collect` or `exact-new`) alongside input and endpoint capacities. `endpoint_corpus_bytes` is actual endpoint capacity times cell width. `conversion_simultaneous_capacity_bytes` sums the input's 4-byte capacity and new endpoint capacity bytes. In `u32-exact` and `u16`, both buffers truly coexist during conversion, giving approximate payload transients of 8N and 6N when capacities equal N; steady endpoint payloads are about 4N and 2N. For inherited `u32`, the sum is only a conservative bound because collection may reuse storage. Allocator headers, other trainer data and allocator retention are excluded; `train_vm_hwm_mib` measures the process peak through training. Conversion time is inside `call_seconds` and `call_cpu_seconds`.

The existing weighted, adjacent, AA and random reference comparisons run through all four modes. Boundary tests still exercise real fresh IDs 65535 and 65536, strict rejection and auto fallback. A long-token test directly compares `u32`, `u32-exact`, `u16` and `auto`, and checks the allocation label and capacity arithmetic. As in the parent, the planning/apply phase barrier and unique owner index are unchanged; no input or index is copied per worker.

# Task-owned context scratch headers

This independent crate preserves the frozen `owned_context` aggregation algorithm, directory and entry allocations, selected rule certificate, owner routing, and posting layout. `--planner hash|context` remains available. New `--scratch-placement borrowed|local` defaults to `borrowed` and only changes where the context producer mutates its scratch header during a planning job.

The original producer borrows a `Scratch` directly from a shared `Vec<Scratch>`. Its header contains the entry vector length and six counters written on context lookups, hits and flushes. Headers are adjacent, with no cache-line alignment contract; different producers may therefore write distinct fields in the same cache line. The current machine reports 64-byte cache lines. This is a false-sharing hypothesis, not a measured hardware-counter diagnosis. It could explain why the earlier context planner reduced hash work in one worker but did not improve four-worker time; other costs and measurement variation remain possible.

`local` replaces its uniquely borrowed header with an empty placeholder, moves the real header into the producer invocation, runs exactly the same closure, then restores it before returning the closure result. Directory and entry buffers stay at their original addresses: no allocation, copy, padding, extra per-position array, or extra per-worker index is added. The shared slot is written at job boundaries rather than at every lookup. The wrapper is non-inlined in both modes to retain a common dispatch boundary; placement is tested once per producer invocation, not per position. This adds O(W) header moves per non-AA batch, whereas the underlying scratch payloads retain their existing bounded sizes. The no-inline wrapper itself is a change from the previous binary, so performance claims must use this binary's borrowed control.

A normal error restores the owned buffers before returning. An unwind drops the local scratch and leaves the safe empty placeholder to be dropped by training; training does not reuse it after unwinding. The placeholder is never passed to planning. No new unsafe operation is introduced. The existing ID-domain proofs for unchecked context addresses remain unchanged. The compiler controls final physical layout; improved time alone would not prove a particular cache-coherence event count.

The CLI reports actual scratch stride and capacity-based header bytes separately from directory and entry payloads. Both modes keep the same Vec allocation. Tests cover buffer identity and state restoration after an error, plus both placements through the weighted/AA/adjacent/random full-reference comparisons. A performance screen must preserve full training-call time, process CPU, training VmHWM, complete ordered rule/frequency/final-token checks, and the same worker CPU affinity. Start with a short screen; do not integrate unless a larger finite check justifies it.

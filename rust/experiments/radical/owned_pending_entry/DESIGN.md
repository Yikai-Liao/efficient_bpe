# Pending owner entries for newborn pair counts

This independent crate starts from the frozen `owned_reuse_accumulator` trainer. It keeps the exact batch-selection certificate, AA parity, corpus writes, keyed birth chains, owner routing, `SmallPosting` layout, heap policies, and call-wide `std|ahash` dispatch. The command-line control is `--owner-commit staged|fused-direct-combined|fused-direct-pending`; `staged` is the original two-phase owner update. Both fused choices transpose producer routes to one exclusive task per owner and use the **same** direct-old update. They differ only in where fresh-pair contributions are counted. The baseline for attributing a pending-entry effect is `fused-direct-combined`, not `staged`.

In both fused choices, a current-batch fresh pair contains an ID at or above `fresh_start`, so it cannot already be in the owner table. Old keys only lose frequency; their deltas are subtracted directly, with checked arithmetic and immediate retirement below `minimum`. Selected old keys have already left the table and are skipped. Eager-heap mode tracks touched old keys and publishes at most one candidate with the final frequency for each. Neither fused mode changes the complete greedy candidate order or posting validation.

`fused-direct-combined` counts fresh `Delta` records in a temporary `HashMap`, then inserts only eligible fresh keys into the permanent owner table. `fused-direct-pending` inserts each fresh key into the permanent table on its first route contribution. Its owner-private `Entry.frequency` accumulates weighted frequency with checked `u64` addition; an empty inline `SmallPosting` stores the checked physical occurrence count in its first initialized `u32` slot. A `(key,count)` touched vector remembers each distinct key. During this private pending phase the posting has `len=0, capacity=0`: empty slices expose no count and `Drop` sees an ordinary inline value. This is a **phase contract**, not a separate Rust type; `push` and sorting must never run on an unmaterialized pending entry.

After every producer contribution is reduced, the owner deletes below-threshold entries and replaces each eligible pending posting with a new `SmallPosting::with_capacity(count)`. The replacement is allocated before overwriting the safe inline value. Birth fill follows each producer's chain, checking its local occurrence count, index bounds, and strictly decreasing nonterminal link. The final posting length must equal the global count. Only then is the eligible fresh candidate pushed to the heap. An error returns from training without another selection epoch; pending inline values, empty reserved heaps, and partially filled postings all drop according to their actual tag and length. No owner table or corpus is copied per worker.

Let `D` be this batch's fresh producer-route records, `B` distinct fresh keys, `E` keys reaching the threshold, and `W` workers. Both fused methods perform `D` expected-time hash updates, scan `B` final keys, and fill eligible birth lists; the chosen hashers do not guarantee constant worst-case lookup. Pending removes the temporary combined map but keeps an `O(B)` touched vector and performs `D` lookups in the possibly larger permanent owner map. Transposed route headers cost `O(W²)`. The temporary count occupies an existing inline field and does not enlarge `Entry` or `SmallPosting`; it does not make allocator overhead zero.

The structural failure case is `B ≫ E`: pending briefly inserts all `B` into the permanent map. Removing rejected keys does not explicitly shrink or free its bucket allocation, so later memory may retain a high-water mark. A commit-stage unit test starts with a small owner table and 256 distinct singleton births at threshold two; it shows this temporary expansion and a higher reported post-retirement capacity **for that stage and toolchain only**. `HashMap::capacity()` is the number of insertions possible without reallocating, not the allocated bucket count: tombstones can lower the reported value on deletion even when the allocation remains. The test is not a proven whole-training memory counterexample, because the trainer's initial index may already have grown the owner map while counting ineligible initial pairs. Conversely, the natural fixtures with weight two and minimum two behave like unweighted minimum one; most newborn keys can be eligible. A favorable result on them cannot establish a general memory win. The experiment does not add periodic rehash/shrink, which would change both work and the comparison.

The JSON output records `fresh_unique_keys` (`B`), `fresh_eligible_keys` (`E`), `fresh_route_visits` (`D`), and direct-old route/hit counts. `B-E` is the number of rejected fresh keys. `owner_entries_*_peak` and `owner_capacity_*_peak` are the maximum across epochs of **sums across owners** at three checkpoints: before the owner commit, after reduction/pending insertion, and after retirement/allocation. The capacity fields use public `HashMap::capacity()` and are not bucket-allocation or allocator-byte counts. In combined mode the middle checkpoint precedes insertion of eligible fresh entries; interpret the modes accordingly. `fresh_scratch_capacity_peak` is combined-map insertion capacity or pending touched-vector slots, and `fresh_scratch_payload_bytes_peak` multiplies that capacity by the key/value or tuple size; both exclude hash control bytes and allocator overhead. `old_touched_capacity_peak`, `expected_capacity_peak`, and `transposed_route_header_bytes_peak` are additional allocation proxies, not additive RSS. `fused_commit_seconds` includes transpose, reduction, fill, and publication. The staged phase timers remain a separate protocol and must not be added to the fused timer. Training VmHWM is sampled immediately after `train` returns; final process VmHWM also includes fingerprint and trace construction.

Local tests compare all three modes against the serial complete result and each other's work counts across both hashers, lazy/eager heaps, one/four workers, weighted AA, adjacent rules, thresholds, and a token longer than 255 bytes. Directed tests force hash collisions, a foreign-only birth, low-frequency removal, malformed chains, pending count overflow, failed materialization, and the commit-stage capacity failure. The shared executor owns Cargo validation, full-trace oracle, and timing; no performance result is claimed here.

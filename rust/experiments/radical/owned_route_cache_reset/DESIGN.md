# Reusing producer route caches with reset replacement phase

This independent crate preserves the frozen `owned_route_cache_reuse` source and its archived results. That first version retained the global two-way `victim_way` replacement phase between batches, whereas its `batch` control constructs a fresh cache with phase zero each time. Exact output remained unchanged, but the phase difference could alter cache hits and evictions. Here a successful batch finish resets `victim_way` to zero after all touched slots have been flushed and cleared. The change isolates allocation and final-scan lifecycle from replacement phase. A failed flush still exits training and drops the caches; it does not enter another batch. All other routing, layout, metric and CLI behavior is carried over. Previous measurements belong to the original phase-retaining binary and are not relabeled as measurements of this one.

This crate copies frozen `owned_route_cache`. `--cache-lifetime batch|reuse` selects the cache lifecycle in the same binary; `batch` is the default control. The pair-key mapping, two-way replacement, grouped birth nodes, owner reduction, heap, AA parity, and selected-rule planning are unchanged. `--route-cache-slots 0|2|4|...|65536` still bounds each producer's slot count; 4,096 slots use 128 KiB of slot payload per producer.

In `batch`, each of the W logical producer jobs creates a cache inside the parallel planning job and scans all K slots when that job finishes, as in the parent crate. In `reuse`, the trainer creates W caches once inside the timed call. Rayon owns them through a parallel mutable slice: each logical producer job exclusively borrows one cache, independently of which physical Rayon thread executes it. The existing atomic task cursor still distributes chunks. This is not thread-local storage.

Reuse mode records the first activation of a slot in an epoch in a touched-index vector and bitset. Eviction flushes and replaces the slot but leaves its touched bit set. At batch completion, the producer visits only its touched indices, flushes any remaining entries, resets every touched slot to empty, clears those bits, and empties the vector. Thus every cached `head` and `tail` referring to a producer-owner birth vector is gone before planning output is returned and before that birth vector can be dropped. The next batch may allocate a new birth vector without inheriting an old index. If planning returns an error or unwinds, the trainer exits and drops the whole cache set; it never proceeds to another batch with partially reset caches.

Each cache still allocates its K slots once. Reuse additionally allocates an index vector with capacity K (`4K` bytes) and a bitset of `ceil(K/64)` words; with K=4096 this is 16 KiB + 512 B per producer beyond the 128 KiB slot payload. Reported upper-bound payload includes actual slot, touched-index capacity, and bitset bytes, but excludes allocator headers, cache object headers, routes, and corpus. `allocated_slots` and `initialized_slots` count cumulative allocations/zero initialization: W×K once in reuse, W×K per batch in control. `scanned_slots` counts full scans in control and touched-index scans in reuse. `touched_slots_flushed` counts reuse batch-final touched indices, including indices evicted earlier in the batch. They are distinct from `flushes`, which counts nonempty slots merged into route maps. The maximum per-batch allocation sum is an upper bound on simultaneous live batch caches, not a measured RSS peak. Reuse caches persist through the batch loop, are dropped before the final token scan, and therefore have a W×K memory floor during training updates.

The lifecycle comparison isolates allocation and final scan costs. It does not adapt K to posting work, change replacement, or permit endpoint writes before all planning jobs and cache flushes finish. Both modes must match the complete reference merge `(pair, frequency, order)` trace and final tokens, including weighted pieces, AA overlap, adjacent rules, and token lengths over 255.

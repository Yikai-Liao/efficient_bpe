# Three update schedules on the same grouped owner state

`owned_fused` copies the frozen `owned_grouped_inline` kernel and changes only how a completed batch applies corpus writes and commits already-planned owner routes. The CLI offers `--commit-mode separate|owner-fused|overlap`, defaulting to `separate` as the control. All modes use the same exact certified batch, posting representation, key owner, dynamic planning tasks, AA parity, final-key birth chains, counted frequencies, and lazy/eager candidate heap policy.

Planning still finishes completely against one stable pre-apply corpus. For non-AA rules, each worker's valid-start vectors move into task-indexed order before the update stage; its route maps remain immutable. For AA, parity-selected Plan chunks and route maps are complete before update. Selected posting lists are released after planning. The apply closure reads the ordered starts or AA Plan chunks and writes endpoint atoms. The owner closure exclusively mutates owner maps/heaps and reads immutable route maps. It does not read corpus. These borrows and independent storage make concurrent apply and owner work data-race-free. Both closures must join before the next rule selection or corpus inspection.

`separate` retains three completion barriers: full parallel apply, parallel frequency reduction across owners, and parallel birth-chain fill across owners. `owner-fused` retains the apply barrier, then executes one parallel owner pass in which each owner reduces its deltas and immediately fills its own postings. `overlap` runs apply and that fused owner pass as branches of `rayon::join` inside the same W-thread pool. The fused pass needs no cross-owner communication: every routed key belongs to one owner, and its local count/frequency are complete after all producer planning jobs join. All three modes use the same per-owner reduce and fill routines, including threshold checks, exact posting capacity, chain count checks, and eager/lazy heap behavior.

The old debug-only check that decodes each planned birth key from the final corpus runs only **after the entire update stage joins**, in all modes. In particular, overlap never reads partly written endpoints for that assertion. Release builds omit this check. A final rule/final-token oracle comparison remains mandatory for both heap policies and all three commit modes, including AA and adjacent different-rule matches.

`update_stage_seconds` is the outer, non-overlapping wall time from route-metadata accounting through apply/commit completion and the post-join birth-key verification in debug builds; release builds omit that verification. `update_dispatches` counts parallel work branches or phases launched; `update_completion_barriers` counts points that must finish before the next phase: 3/3 for separate, 2/2 for owner-fused, and 2/1 for overlap's two joined branches. These are logical counts, not Rayon API-call counts. `apply_seconds` is its branch wall time. Only separate has globally separated `frequency_reduce_seconds` and `birth_group_fill_seconds`; in fused modes per-owner reduce/fill work is reported as sums and maxima, and a fused owner-branch wall time is separate from the outer update time. A branch timer includes scheduling and waiting, so its sum is not pure CPU service time. Branch timers may overlap and must not be summed with `update_stage_seconds`. The comparison keeps the same layout and avoids extra corpus or index copies; temporary Plan and route lifetimes remain inside the update stage and its process-memory peak. The CLI also reports `call_cpu_seconds` using the same process-CPU clock and before/after sampling order as the native benchmark binary.

# Producer atomic reduction of old pairs

This independent crate copies the frozen `owned_pending_entry` implementation, but its benchmark CLI exposes only `--old-reduce owner|producer-atomic` (default `owner`). Both choices use `Entry { frequency: AtomicU64, positions: SmallPosting }` and the same `fused-direct-combined` fresh-key path. The copied library still contains its staged and pending modes for inherited regression tests; the CLI cannot select or combine them with producer atomics. `--integer-hash std|ahash`, heap policy, batch certificate, AA parity, corpus, routes, and posting layout are otherwise unchanged. The owner choice is the causal control. With eager heap, a requested producer-atomic choice executes owner reduction and reports the effective mode, because eager final-frequency publishing would require another touched-key protocol.

During selection, all selected Entries leave the owner dictionaries. From then until every producer planning job joins, the owner maps are structurally frozen and are shared read-only. Each worker still aggregates old pair deltas in its own owner-route maps; there is no atomic action per occurrence. After finishing its assigned plan tasks, a worker calls `HashMap::retain` on each route: fresh keys stay; each old key with a missing owner Entry is dropped; each found old key causes one `AtomicU64::fetch_sub(Relaxed)`. If this operation first crosses `minimum`, the old route item stays as the unique retirement marker; every other old item is removed. No extra retirement queue or copy of a posting index is allocated. The public map's bucket capacity does not automatically decrease when route items are removed. `old_route_records_before_flush` and `preflush_route_capacity_peak` preserve counts from before this in-place scan.

All producers join before corpus apply completes and before owner commit starts. In producer mode the owner sees only fresh route records and retirement markers. A marker must point to an existing Entry whose final frequency is below `minimum`; the owner removes it and drops its posting without subtracting its `Delta.weight` again. Fresh keys still go into the separate temporary combined map, pass the same weighted frequency threshold, reserve exact counted posting capacity, follow the same producer birth chains, and publish heap candidates only after the final length check. In owner mode, the owner instead processes all old route records itself using `AtomicU64::get_mut()` and checked subtraction under exclusive access, then uses the identical fresh path. Both modes therefore isolate producer-side old reduction from pending-entry counting and accumulator reuse.

Correctness depends on the original planner's non-overlapping selected matches and neighbor-edge suppression. An old key has IDs below this batch's first fresh ID and can only lose frequency; all new edges contain a fresh ID. Producers sum piece weights locally before touching a shared Entry. The fetch-sub operations for a given key have a total order and, for valid route deltas, exactly one can cross `minimum`; it leaves one marker. A selected key has already been removed from the map, so a local delta for it is ignored. `Relaxed` suffices for the frequency word because no planner decision uses it and Rayon join precedes structural deletion, heap refresh, and next-batch selection. The corpus is not written until planning returns; the owner map is never changed while workers hold shared references. On `old<delta`, the atomic has already wrapped, so that private training call joins all jobs and returns an error without starting another epoch. No reusable trainer state is exposed on error.

This does not remove the W-by-W route headers, their allocated bucket capacity, or the shared old-key dictionary lookup. `atomic_old_calls` counts one RMW for each found producer/key, not each occurrence. `atomic_retire_markers` counts threshold crossings; marker count can be far smaller than `old_route_records_before_flush`. The owner mode may stop looking up a key once it retires, whereas producer mode still subtracts all valid fragments, so their old-entry hit counts need not match. Worker flush time is reported as `atomic_flush_worker_seconds_sum`, a **sum across workers already included in plan wall time**, never an additive stage wall time. The producer can overlap reduction with other workers' planning and shorten owner commit; hot-key cache-line contention, nearby Entry false sharing, extra `retain` scanning, and W=1 overhead may make it slower. `HashMap::capacity()` is only a public insertion-capacity proxy and cannot be equated with allocated bucket bytes or RSS. Training VmHWM is sampled before fingerprint/trace construction.

The inherited full-trace comparison exercises both hashers, lazy/eager policy, AA, weighted adjacent rules, thresholds, and long tokens. Two scoped-thread tests start producer flushes together: one checks weighted frequency 10→3 across the threshold with exactly one marker and one owner deletion; the other forces an underflow and checks that the private state is discarded rather than committed. Complete-trace oracle and performance verification are delegated to the shared executor. The separate [protocol review](../../../ATOMIC_OLD_REDUCTION_NEXT.md) records the work bound, counterexamples, and measurement contract.

# Inline two posting positions per pair key

This independent variant preserves the frozen `owned` v5 algorithm and replaces `Entry.positions: Vec<u32>` with a 16-byte `SmallPosting`. The representation is `#[repr(C)] struct SmallPosting { len: u32, capacity: u32, payload: union { inline: [u32; 2], heap: *mut u32 } }`. `capacity == 0` means inline mode and `len <= 2`. Heap mode has `capacity >= 4`, `len <= capacity`, and `heap` is the live allocation pointer from one `Vec<u32>` of exactly that length and capacity. No pointer is converted through an integer. A moved `SmallPosting` transfers unique ownership; safe slice borrows tie their lifetime directly to `&self` or `&mut self`.

`push` writes inline while `len < 2`. The third item builds a four-slot Vec from the two inline values and installs its raw parts only after all fallible allocation and capacity checks complete. A heap push with spare capacity writes through `ptr.add(len)` and increments `len`. On heap growth, it first uses `mem::take(self)` to leave the destination in an empty inline state, reconstructs the old Vec from raw parts under a non-dropping wrapper for the moved source, reserves and pushes, checks that actual capacity fits `u32`, then installs the new raw parts. If reserve panics, the temporary Vec is the sole owner and frees the allocation during unwind; the destination remains empty. A checked numeric-capacity error before reconstruction leaves the original posting intact. An actual allocator capacity beyond `u32` after reserve returns an error and drops the temporary Vec; the trainer aborts rather than continuing with an emptied posting. The current corpus contract makes this case unreachable in practice. Ordinary allocator OOM follows Rust Vec allocation behavior, with no duplicate owner during unwind.

`as_slice` and `as_mut_slice` construct slices of length `len` from the active inline array or heap pointer. `Drop` reconstructs and drops the heap Vec exactly once, and does nothing for inline mode. `take` uses `mem::take`, leaving an empty inline source. Unsafe `Send` and `Sync` are justified by unique heap ownership, ordinary `&mut` access for mutation, and no interior mutability; worker threads only borrow immutable selected postings during planning. Tests cover lengths 0/1/2/3, multiple growths, move/take/drop, 64-bit layout, cross-thread ownership and shared reads, AA sort through a mutable slice, and the existing exact oracle cases. The final source passed 7/7 debug tests, strict Clippy and release build, 80/80 full oracle comparisons, and 20/20 quick full traces. A 4 MiB timing screen has not yet been run.

The intended memory effect is smaller map records and fewer allocator calls for short postings. The measured 64-bit layout is `SmallPosting` 16 bytes, `Entry { frequency, positions }` 24 bytes, and `(key, Entry)` 32 bytes, versus 24/32/40 for Vec-backed postings. Metrics use `allocated_capacity()`, which reports zero heap slots for inline mode; the two inline slots are already part of the map entry. Final inline/heap key counts and actual heap position capacity are reported separately. These are final-state counts, not a peak RSS claim. The final owner-stat scan is timed separately. It also folds v5's two values scans into one scan while adding inline/heap counts, a small real code difference that prevents attributing all end-to-end timing changes solely to allocation or destruction. The early selected-list drop, initial indexing, owner routes, heap policy, and exact batch semantics remain unchanged.

# Sparse owner actor: source review

**Scope (2026-09-30):** This is a read-only review of [`parallel_sparse_owner.rs`](src/ablation/parallel_sparse_owner.rs), separate from the proposed protocol in [`SPARSE_OWNER_DESIGN.md`](SPARSE_OWNER_DESIGN.md). It does not report test or benchmark results. I found no concrete missed-holder, stale-head, or phase-ordering counterexample in the reviewed implementation.

The initial scan routes each producer's local counts with its group bit, and scalar owners OR those bits before the second, globally filtered index scan (`Router::route`, `PairState::initialize`, `BuildIndex`). For a fresh key, every emitted `NewEdge` contributes a positive delta from its producer; `PairState::reduce` ORs the positive contributors into the birth mask before checking global frequency. A below-minimum fresh key is inserted into `retired` with that temporary mask, so all potential producers receive a prune verdict and suppress provisional edges during `Apply`. An old key's stored mask is not expanded: in this fresh-ID scheme a newly created edge contains the new ID, so an old key cannot acquire a new location. Negative delta for an absent old key is ignored; positive delta is rejected.

`PairState::top` uses a non-destructive heap peek. It validates the peek against the owner's current scalar frequency, discarding or lowering stale entries before returning a `Head`. The coordinator caches one exact head per owner. All delta destinations are marked in `touched_owners`, and the selected pair's owner is forced into `Reduce` even if no producer marked it. Each participating owner reports a new strict top after applying its complete epoch delta; only those cache entries change. Owners omitted from `Reduce` have neither scalar changes nor fresh keys, so their cached heads remain exact. An owner's selected pair must reach zero or the run errors.

AA is gathered from every worker in the selected key's holder group expansion. The coordinator sorts all live starts and selects non-overlapping matches left to right before dividing that selected vector among the same workers. Planning uses the **global** selected vector for left/right adjacency, including across slice boundaries. Group-mask false positives return empty fragments but do not omit true holders. New pair masks are built from the workers that actually plan the selected slices.

The coordinator writes the shared token-length Vec before dispatching a rule. Each active planner takes one read guard around planning, releases it before routing deltas and sending `Prepared`, and no new write begins before all `Apply` replies. Every producer routes delta before `Prepared`; the coordinator waits for all `Prepared` replies before `Reduce`. Owners publish prune records before `Reduced`; the coordinator waits for all `Reduced` replies before `Apply`. Prune records carry the epoch, and a prune-only worker has no plan for that epoch; `Apply` drains its mailbox and only writes endpoints if it actually planned. The next rule is not chosen until every dispatched `Apply` completes. Atomic corpus cells avoid Rust data races, while these phase barriers provide the stable-snapshot semantics.

The per-round coordinator path iterates only the selected holder-group expansion, touched owner-group expansion, and their apply union. `Router::route` drains only nonempty destination buckets. There is no loop over all W workers in the merge loop. The router still allocates W bucket headers **per worker** at initialization, so its resident control metadata is O(W²), and final capacity reporting scans all buckets. Group expansion can conservatively wake up to `ceil(W/64)` workers per bit when W > 64. The AA fallback still requires coordinator-side sort and selected-position storage; sparse activation does not remove that serial phase.

Useful regressions remain a rare fresh pair born in two producers whose partial counts only jointly reach `min_frequency`; a fresh below-threshold pair with a provisional edge; a stale cached old-key top whose frequency falls to zero; AA runs whose overlapping starts cross worker or group boundaries; and a worker that only receives a prune after skipping several epochs. These exercise the invariants above rather than asserting implementation-specific visit counts.

## Initial routing capacity and the dense comparison

The sparse worker creates W reusable `Vec<Delta>` buckets before its first count scan. The initial count map is consumed through `Router::route`; `Vec::append` empties each source bucket while retaining its capacity for future routes. The owner initial inbox is drained and `shrink_to_fit` is called, but the producer router and its W bucket headers live until that worker exits. Thus capacities reached during high-cardinality initialization may remain resident across all merge epochs, even if sparse per-epoch deltas are small. The final `router_capacity_entries_sum` reports retained **entry capacity**; it omits W Vec headers per worker and does not itself measure RSS. The dense pair-owned version constructs route buckets inside each call and drops them at return, while it also shrinks the drained initial owner inbox. Its initial routing allocation has a shorter lifetime. This distinguishes the implementations beyond the sparse scalar's extra 8-byte holder mask per key. Conversely, sparse shares one token-length vector rather than keeping one copy per worker, and avoids dense candidate pages/leases; it adds prune mailboxes and an O(W) cached frontier. Initial peak overlap, allocator retention, and measured RSS cannot be assigned a numeric cause from these structures alone.

## All-worker dispatch ablation

The `ALL` branch sets the plan, owner-reduce, and apply masks to every worker but leaves the selected pair's stored holder directory unchanged. On AA rounds, every worker receives `GatherSelf`; only workers from the original holder-group expansion get nonempty ranges of the globally selected, left-to-right starts. The other workers receive `PrepareSelf(0,0)`, which completes their gather epoch, then all workers receive `Apply`. On ordinary rounds extra planners remove an absent selected-key fragment and produce no matches under the holder invariant. Extra owners reduce an empty inbox and report their existing strict top; extra apply workers drain an empty prune inbox and have an empty plan. Thus the valid-state merge trace should be unchanged.

This ablation includes **empty actor work**, not just message latency: extra planners acquire the length read lock and construct empty delta maps, extra owners lock mailboxes and validate local top, and extra apply workers allocate/check prune sets. On AA, the extra gather also probes the selected-key index; if an incorrectly omitted holder actually has a fragment, `ALL` might discover it and differ from sparse mode, exposing rather than proving away a directory bug. The meaningful comparison is all-worker activation versus sparse activation under the same actor implementation, with active-worker counts and phase times alongside total time.

# Exact batch training with position and pair ownership

This is a proposed implementation path, not an implemented speedup. The invariant to preserve is the **ordered** `(pair, weighted frequency, fresh ID)` rule sequence and final tokens. Position visits and stale visits are implementation counters. The proposal uses the certified, consecutive non-self prefix described in [PARALLEL_RETHINK.md](PARALLEL_RETHINK.md) and the [batch-end adjacency proof](PARALLEL_RESEARCH_OWNERSHIP.md#direct-batch-end-adjacency-update-conditional-design); if the first candidate is `AA`, execute one self rule with its separate run-parity protocol. A physical block never inserts a token or separator into the corpus.

## What the current modules actually own

- [The serial ablation trainer](src/ablation/trainer.rs) builds a single `Index` and `Queue`. `certified_prefix` at lines 217–273 only prefetches rules; the authoritative loop still applies them serially. [The index trait](src/ablation/index.rs) exposes one mutable index with per-key positions; its `Separate`, `Combined`, and arena implementations are not independently writable shards.
- [The snapshot occurrence worker](src/ablation/parallel_occurrence_snapshot.rs) uses one shared atomic corpus, so it supports a continuous string. But the coordinator scans all initial positions into its global maps (lines 433–453), gathers every validated position and runs `select_plans` serially (lines 563–599), then iterates worker results' per-position new occurrences into the global map (lines 649–675). Its worker delta map already reduces frequency traffic to distinct keys; its global position reducer and plan are the remaining O(matches) coordinator work.
- [The piece worker](src/ablation/parallel_piece.rs) keeps a local position map, but `shards` assigns whole separator-delimited pieces (lines 29–68), so a single continuous piece gets one worker. The coordinator still combines every worker's initial counts and round deltas into one frequency map/heap (lines 383–412 and 502–534). `owner` means a worker-dispatch mask here, not ownership of pair frequency state.
- The public [validation scan](src/trainer.rs) currently makes a serial pass over every original position, checks dense IDs and separators, and sums weighted adjacency (lines 176–208). Merely parallelizing the later merge loop leaves this O(N) initialization bottleneck. Conversion of owned `Vec<u32>` into the snapshot's `Vec<AtomicU32>` is another one-time corpus pass and may raise peak memory during conversion.

The worker-local batch kernel is now implemented in [parallel_certified.rs](src/ablation/parallel_certified.rs), with initial evidence in [the batch report](BATCH_PARALLEL_REPORT.md): keep occurrence fragments on the worker that **generated** them, let workers compute final batch edges from a frozen snapshot, and reduce only per-key deltas on the coordinator. It removes coordinator O(matches) position assembly for non-self batches; AA still uses a global gather and sort. Its coordinator still does O(distinct touched keys) updates and owns the only heap. Its dynamic fragment placement can drift away from physical corpus positions, concentrate a hot pair's historical list on one generating worker, and cause remote NUMA reads on later rounds. Dynamic placement may save an explicit boundary-position transfer and may sometimes use fewer per-shard key entries; the trade must be measured. This is the first step, not the full pair-owner design below.

## Recommended next step: static start shards, scalar pair owners

Use `W` long-lived worker threads, each with two roles in separate phases; do **not** create another W owner threads. Partition the original position interval into W contiguous ranges. `owner_start(p)` never changes; a worker owns historical occurrence records whose **left token starts** in its range. The single continuous endpoint corpus remains shared. A selected pair whose tokens cross a range boundary is still one valid occurrence; matching and weights use the real adjacent tokens. Initially an atomic `u32` cell per original position is the safer shared layout. Nonoverlapping match spans permit concurrent writes, but a packed bitmap or nibble backend needs a separate word-ownership proof. A future unsafe plain-u32 layout should be an isolated, audited optimization rather than a premise of this architecture.

Independently, `owner_pair(key) = stable_mix64(key) % W` gives every packed pair exactly one **scalar owner**. That worker owns the pair's exact `u64` frequency and its entry in a strict local heap. It owns no full occurrence vector for the key; the start shards retain those fragments. A pair owner may keep a compact directory of shards that have a fragment so it can retire an ineligible key without broadcasting every key. A hot pair then costs its pair owner one count and at most W fragment summaries, while its matches remain distributable across position workers. Pair-owner hashing must mix both `u32` halves; assigning by the fresh ID high half alone would cluster new pairs.

The minimum implementation may broadcast a batch's keys to all W start shards and omit the directory. That costs O(W × batch width) small control records per epoch but avoids per-pair W-bit storage. Add a directory only if measured dispatch costs justify it: a `u64` mask for W≤64, or a sparse shard-ID list/bitmap chosen by density for larger W. Never allocate a full W-bit mask per historical singleton by default. Require a minimum original-position grain when choosing W; otherwise `Σ_i K_i` hash entries and thread stacks can dominate a tiny corpus. Expose that grain and measure sensitivity rather than tuning it to one fixture.

### Parallel initialization, including validation

1. Validate scalar metadata (`lengths`, pivot order/boundaries, weights, ID-capacity limits) with checked accesses. In the first parallel corpus pass, each start shard checks IDs/separators and counts its own initial edges. A global atomic alphabet bitset, or compressed per-shard seen-ID summaries, checks that every dense initial ID occurs. Each shard accumulates weighted adjacency in `u128`; combine W scalar sums and reject totals above `u64::MAX`. This replaces the current separate serial O(N) validation pass. Checked reads are mandatory until all shards finish validation; only then may an unchecked hot path rely on the validated invariants.
2. Each shard groups its initial weighted counts by pair. It partitions **key-level** partial counts directly into pair-owner mailboxes. Pair owners sum all shard contributions with overflow checks, filter against `min_frequency`, and build their own exact heaps. The coordinator does not iterate all corpus positions or reduce all keys.
3. For the low-memory version, owners return globally eligible keys only to the shards that reported that key. After local temporary count maps have been consumed, shards make a second parallel scan and build `pair→Vec<u32>` fragments only for those keys. The extra O(N/W) pass avoids storing positions for globally rare initial pairs. A one-pass, store-all initialization is a separate speed/memory ablation, not the default low-memory claim.

The pair owner must decide eligibility from the **global** weighted sum: filtering a shard's local count at `min_frequency` first would drop a pair whose small counts on several shards add up to an eligible rule. Piece weight lookup remains tied to original pivots, including a piece that spans several physical shards.

### One certified epoch

1. Each pair owner validates its heap top against its current exact frequency and publishes one `(frequency,key)` summary. The coordinator takes the strict maximum using frequency descending and packed key ascending. To extend a prefix, it requests each winning owner's next exact candidate, as in a W-way merge of owner heaps, and stops at the **first** head/tail conflict, self pair, rule cap, or exhausted candidate. Owners keep tentatively popped entries aside until commitment; a stopping candidate is reinserted. Across a prefix of B rules this is O(W + B log W) coordinator comparisons plus owner-local heap work, not O(occurrences) or a relaxed priority queue. Fresh IDs and token lengths are assigned in that certified order.
2. Broadcast the chosen metadata (or send only to indexed shards once a directory exists). Every start shard moves its selected historical Vecs out of its local index without copying them. Against one immutable pre-batch corpus, it validates live starts, computes the selected rule's weighted matched sum, reads `X,L,A,B,R,Y`, and builds **batch-end** signed pair deltas and grouped new-edge starts. Heads and tails being disjoint make all selected spans token-disjoint. The left selected match owns a shared boundary; it deletes the old boundary and emits the final `(Z_i,Z_j)` directly. No coordinator reads each position. Before write commitment, an owner can compare the sum of validated weighted occurrences for each selected non-self rule against its exact pre-batch frequency; mismatch signals a missing or duplicate live index record.
3. Barrier: every snapshot read and every plan must finish before any corpus write. Then start shards write their selected disjoint spans concurrently. A selected-start Vec can be retained and filtered in place during planning, then replayed for writes, avoiding a separate wide `Plan` Vec. Endpoint writes may cross a static shard boundary; the match start owns the write, and shared `AtomicU32` cells avoid a native data race. Route worker-local `HashMap<pair,i128>` deltas in **batches by pair owner**, and stage new grouped positions locally. `i128` sums are combined for the full epoch before changing any `u64` frequency; applying senders in arrival order could otherwise cause a false temporary underflow.
4. Barrier: after all writes and delta batches are submitted, each worker switches to its pair-owner role, processes its inbox, retires selected/low-frequency keys, inserts genuinely fresh eligible keys, and validates its local heap. Workers publish exact owner maxima; the coordinator may certify the next prefix only from the completed epoch. New pair keys contain a current-batch fresh ID and cannot have existed before this batch. Their **final batch count** decides whether to retain staged occurrence fragments; below-min keys cannot revive in a later epoch because old-ID pairs only decrease. Owner decisions can return directly to fragment-holding shards while the coordinator merges candidate summaries; no coordinator key loop is needed.

For new `(L,Z_i)`, the occurrence start is `L`'s original start, which can belong to a different start shard from the match at `A`. Route that start to `owner_start(L)`, not to the producer, after eligibility is known. `(Z_i,R*)` starts at `A` and stays local. Because start ranges are contiguous, at most one live adjacency crosses any static range boundary in a path at an instant. Therefore at most W−1 newly generated *left-edge starts* need cross-shard routing per epoch for one continuous path (and no more than W−1 total across all pieces); one very long token may skip several ranges but still represents one crossing edge. This bound is lost when fragments remain with arbitrary generating workers. It does not bound the number of **key-level** delta messages, which is controlled by distinct touched keys.

The minimum synchronous implementation has a global plan/read barrier, a corpus-write/mailbox barrier, and owner-completion before the next selection. Eligibility replies and local index pruning may overlap coordinator candidate comparison, but all fragments needed by the next prefix must be committed before its plan starts. No per-position coordinator barrier is allowed. Batching amortizes these barriers over B exact rules; a long dependency chain may still give B=1.

### `AA` when a run crosses physical shards

The pair owner reports `AA`'s **overlapping** weighted frequency as the rule frequency. If it is the first candidate, execute it alone. Its position shards validate local AA edge starts and order them by physical start (sort/radix if historical append order is not guaranteed). Consecutive valid starts `p` and `p+len(A)` are overlapping edges of the same AA run. Each shard sends only its first/last valid start, leading/trailing run lengths modulo two, and whether its whole valid set is one run. The coordinator performs an O(W) ordered prefix scan of run parity, including empty shards that a long token spans, and sends each shard its incoming parity. A shard then selects even-offset edges in each run, reproducing global left-to-right nonoverlap; each selected token span is disjoint. For AA the generic pair-type membership test cannot tell whether a neighboring AA occurrence was selected: the worker must use selected-start parity/flags when constructing final edges. The same stable-read/write/owner-update barriers apply. A serial AA fallback is acceptable for an initial correctness milestone, but it is not a multi-core solution for a long continuous run.

## Space, complexity, and failure boundary

Let N be original positions, W active start shards, `K_i` the distinct retained keys in shard i, `H_i` the **length** of its retained historical position Vecs, `C_i` their **capacity** in u32 entries, P distinct active pair scalars, B certified rules in an epoch, M live matches in that epoch, and D distinct `(producer shard, pair owner, pair key)` signed deltas. Measure `Σ_i K_i`, `Σ_i H_i`, and `Σ_i C_i` separately. `4Σ_i C_i` is the position **buffer capacity**, not total index memory: each hash entry, Vec header, map bucket, owner count/heap entry, fragment directory, thread stack, and staged message also occupies memory. The shared atomic corpus is 4N bytes after construction, with possible conversion peak above 4N. There is one scalar frequency entry per pair owner, not W copies of the full P-key frequency table. In the worst case `Σ_i K_i` can approach `min(WP,Σ_i H_i)`, so excessive sharding can erase the byte savings of 4-byte offsets.

For historical offsets, initial retained edges are at most N and each actual replacement creates at most two final new edges. Since every replacement removes one live token, total replacements over training are at most N; cumulative appended offsets are at most roughly `N+2N=3N` (before eligibility filtering). This is an **entry-count** bound, not a Vec-capacity or allocator-RSS bound. Keep old pair Vecs only while the pair can meet `min_frequency`; discard an old key permanently when its exact global count falls below the threshold. Retain new-key fragments provisionally until the *whole batch* count is known, then drop below-min fragments before the next plan. Remove empty map entries so `Σ_i K_i ≤ Σ_i H_i` for retained fragments. If a fresh eligible key appears in many shards, its fragment metadata still costs one `K_i` entry per participating shard; use a minimum shard grain and measure that fragmentation. Never copy the full corpus or full occurrence index per worker.

An operational peak-memory ledger is `4N + 4Σ_i C_i + map_bytes(Σ_i K_i) + owner_scalar_and_heap_bytes(P) + 4C_stage + delta_map_bytes(D) + mailbox_bytes + plan_bytes + validation_bytes`. Count detached selected Vecs in `Σ_i C_i` until consumed. `C_stage` is the **capacity**, not length, of provisional new-position buffers: at most two *logical* final edge starts arise per match, so their length is ≤2M, though Vec growth and hashing increase capacity/RSS. For the non-self prefix, compacting valid starts into their moved selected Vecs makes extra per-match `plan_bytes` close to zero; the Vecs themselves still occupy space, and the AA sorted/parity path may need O(M_AA) scratch. `delta_map_bytes(D)` includes hash-table capacity, not merely `16D` payload bytes. During two-pass initialization, add the temporary `Σ_i local_count_map_capacity` to the ledger until those maps are consumed; no occurrence Vecs have yet been built. Record each term's *simultaneous* high-water mark and process RSS, rather than summing maxima observed at different times. Pair-scalar ownership avoids W full copies of the P-key frequency map, but it does not erase the `Σ_i K_i` fragment maps.

The non-self read plan visits only selected historical offsets plus O(1) neighbors per valid match: O(H_selected) work distributed by start shard. It may retain the moved selected Vecs and at most O(M) final new offsets, instead of allocating a coordinator `Valid` plus wide `Plan` plus flat result stream. A worker's signed-delta table is O(distinct touched keys), with at most about five edge contributions per match before local cancellation; messages are O(D) key records, not O(M) frequency updates. Pair owners perform O(D + Q log P_owner) work per epoch for Q affected/fresh heap entries in aggregate, distributed across W owners; the coordinator processes O(W+B log W) candidate summaries and O(B) rule metadata. The best possible wall time remains limited by load skew, barriers, local hash work, and AA parity; these are design bounds, not measured speedups.

The most dangerous correctness boundaries are incomplete/duplicated live starts; a weight pivot or sentinel at a static shard boundary; AA parity over empty shards or a token spanning several ranges; two writers touching the same *packed metadata word* despite disjoint token spans; pair-owner updates before all signed deltas arrive; and a lazy heap reporting a stale upper bound as an exact winner. Keep message queues bounded to one epoch, reject errors before publishing a partially updated next state, and test complete ordered traces against the serial oracle. Report separate validation/init, candidate, plan, apply, pair-owner, prune, barrier wait, and final-traversal times, plus peak RSS and every capacity above. The meaningful speed test compares 1→2/4/6 workers within this same implementation and against the best direct serial trainer, including its initialization cost.

# 将位置列表与频率交给同一个 owner（后续设计，尚未实现）

当前两条路线各解决了一半问题。原生 `parallel_pair_owned` 已让频率和堆按 key 唯一分片，但同一个 key 的位置仍散落在多个 worker 的局部索引中。radical v4 让位置只存一份，并按小块动态分工，但中央线程仍归并全部 delta 与出生记录。本设计把这两个决定接到一起：**key 决定存储归属，位置块决定执行归属**。工作线程可以处理任意 owner 的冻结位置块，处理产生的变化则回到相应 key 的唯一 owner。

这不是已实现的版本，也没有速度结论。先等待 v4 的批量实验和 boxed 的独立存储实验，再决定是否实现。下面给出它需要改变的关键路径、精确性条件及内存边界，避免把简单拼接误认为免费收益。

## 不再要求所有位置列表按位置排序

v2 的单规则写入器用相邻 Plan 判断 `ABAB` 的共享边，因此依赖位置顺序。v4 的非 AA 规划器已改为读取同一稳定语料快照，通过选中 key 表判断左右相邻匹配。它只要求一条有效出现被处理一次，**不要求该 key 的位置有序**。不同匹配不重叠，写入端点也互不相交；最终出生边由左匹配唯一生成。

因此，后续 owner 可以按任务完成顺序接收并追加某个新 key 的位置。合并顺序仍由精确频率和 key 同频顺序决定，位置列表的内部排列不参与优先级。非 AA key 从出生到退休都无需排序。AA 仍必须按语料从左到右选取：在选中该 key 时，才对它的列表按位置排序，再使用已有的跨块 run 奇偶摘要。历史坐标可能已经失效，但排序后过滤不会改变有效坐标的顺序；每个 AA key 最多被选中一次。

延迟排序可以省去大量非 AA 出生记录的比较排序，不能宣称最坏排序复杂度消失。若用比较排序，所有被选 AA 列表的成本仍有 `Σ Haa log Haa` 项。后续可以单独比较整数排序及其额外缓冲，首版无需加入。

## 一个批次的所有权与屏障

1. 每个 owner 发布小段已校验候选。协调者选择与当前精确批次相同的连续类型安全前缀；耗尽某个 owner 的已发布页时，必须向它续页，不能跨过尚未发布的更高频或同频更小 key。AA 独立一轮。只将选中条目的位置列表移出 owner 表，不复制列表内容；未选候选按原协议归还。
2. 完成需要的 AA 排序后，将选中列表和规则参数放进本批只读容器，例如持有各 Box 的 `Arc<Batch>`；只共享容器引用，不复制位置。任务目录只保存 `(rule_rank, start, end)`。持久 worker 动态领取任务；每个块的所有快照读取完成前，任何 worker 都不能修改语料。列表从 owner 表移出后也不能提前 drop，本批容器必须覆盖所有读取者的生命周期。
3. worker 在本地生成紧凑有效起点和旧边扣减、最终新边。变化按 key 哈希路由到唯一 owner。同一个位置块的执行者与目标 key 的 owner 无须相同。相邻选中匹配的共享边仍只生成一次。
4. 所有快照规划与路由完成后，端点写入和 owner 归约可以并行执行。owner 汇总完整批次变化后，才对新 key 判断频率阈值，并构造其唯一位置列表。旧 key 只减频，不扩展位置列表；低于阈值即可释放它的列表。
5. 新频率、出生列表和端点写入全部完成后，才允许下一批读取语料。此时丢弃本批选中列表与任务引用，候选前沿进入下一轮。不能把“全部任务已经被领取”当作“全部读取已经完成”。

AA 在第 2–3 步之间仍有自己的摘要屏障：先按序过滤出有效 AA 边，收齐各 chunk 的 run 摘要，再计算入块奇偶，随后生成实际选中的 Plan 与边变化。`AAA` 有两个重叠的 AA 出现，不能仅凭 `selected-key` 就把左右两个出现都认作本轮选中的匹配。这里保留现有 AA parity 路径，不能把非 AA 的邻居判断直接套过去。

这里保留现有精确批次的证明：选中旧 pair 的有效出现互不重叠；所有新边对应一个未选旧 pair 的出现，因此频率不会越过批内后续选中规则，fresh ID 也不会在同频时提前。共享位置列表不会引入按空格或预分词边界切割，唯一边界仍来自完整语料中的实际 token 端点和已有 piece 哨兵。

## 路由缓冲不能跟每个小任务相乘

若每个动态任务都分配 W 个目标桶，G 个块会产生 `O(GW)` 个 Vec 头，细分任务反而扩大内存。应由 W 个持久执行者各保留 W 个路由桶，只给实际触及的目标追加数据，在规划结束时按桶转交，Vec 头是 `O(W²)`；位置块结果只保存有效起点及规则分组，任务目录和结果元数据仍有 `O(G)`。若把执行者与 owner 分为 P、O 两组，桶头界应写 `O(P·O)`。跨轮保留 payload capacity 需要单独限额或回收，不能重演 sparse 初始化路由桶长期滞留的问题。

规划阶段 owner 也可能正在执行位置任务，因此不能向一个尚未被接收的有界 inbox 持续阻塞发送；否则所有执行者都可能等在路由上，永远到不了归约阶段。首版可在每个 producer 的本地桶完成聚合，再在屏障后转交所有权。逐任务发送 W 个消息也会重新引入 `O(GW)` 的控制开销。

这并不消除 `O(W²)` 的几十核开销。还应比较稀疏 touched-owner 目录，但不要为省几个桶头重新加入逐边锁。Rayon 的 `fold` 或 `for_each_init` 不天然保证只生成 W 个累积器，不能仅凭用了线程池就写出 `O(W²)` 空间界。若复用原生持久 actor，必须显式证明每个执行者只有一套缓冲。

每个 key 只保存一份频率、一份堆归属和一份历史位置列表。临时跨 worker 路由可能复制出生记录，需同时计量“持久位置”“尚未归约的出生位置”和对应 capacity。owner 可以先用 Vec 聚合，再选择是否转为 Box；后者可能复制或缩容，不得省略分配成本。完整构建后再过滤低频 key，意味着短暂存储不合格位置，这也是需要实测的代价。

## 验收与反例

与 v4 比较时固定证书、输入、CPU 总预算和初始索引方法，先改变 owner 归并与出生构建；AA 延迟排序若一起加入，须单列其耗时和位置量。需要报告中央逐记录处理是否真正消失、路由/归约/AA 排序/出生构建的阶段时间、每批宽度、worker 工作量分布、列表和路由峰值以及 VmHWM。

正确性对照必须覆盖打乱的非 AA 列表顺序、跨任务相邻的不同规则、`ABAB`、跨块 AA 长 run 与空块、权重不同的独立 piece、长 token 和频率阈值淘汰。随机调度只能验证结果是否依赖完成顺序，不能代替静态的唯一写入者与屏障证明。

当前机器只有六个可见 CPU。这条结构有望减少中央关键路径及重复索引元数据，但不能预先声称它能在双路服务器上近线性扩展。统一 owner 上的热点、跨插槽读取语料、邮箱流量和短尾批次，仍可能分别限制速度。

## 最小实现路径与可隔离的内存改动

两位独立审查者均未找到上述精确性条件的反例。实现优先从 v4 的 Rayon 阶段开始，而不是重写原生 actor 消息协议：保留证书与 AA 路径，显式创建恰好 W 个作业，共享一个原子任务游标；每个作业维护自己的一套路由桶。有效起点存入以 task 下标定位的结果槽，不能按完成顺序猜测 rule rank。作业 join 后，只搬动桶的 Vec 头以转交各 owner，再对互不重叠的 owner 状态并行归约。这仍有每轮派发成本，但借用期与屏障更容易明确；若实测派发成为关键路径，再考虑持久 actor。

Box 与 v4 合并时，应把可复制规则参数与不可复制 posting 所有权分开。当前 v4 的 `FlatTask` 是 arena 绝对偏移，改为 Box 后需变成该规则列表的相对偏移；全部规划 join 后，应用阶段只需要规则参数和有效起点，可以及时释放选中 Box。选中列表不再与新列表共存，但出生临时记录和新列表仍可能同时占用内存。

另一个可单独测量的布局是让出生路由桶**只存 `u32 pos`**。规划者已经知道最终 key，可据此选择 owner 桶；等本批全部端点写入完成后，owner 从 `corpus[pos]` 和 `corpus[pos + length[id]]` 读取最终 key。这会将每条路由记录的逻辑载荷从 `(key, pos)` 的 12 字节（Rust 普通 tuple 往往为 16 字节）降为 4 字节，也适用于初始位置路由。共享边必须仍由左匹配唯一生成，哨兵边不入桶，生成的 anchor 必须是最终活 token 的起点。

这种布局增加语料读取，并要求 **全部端点写入完成之后**才能解码出生 key。owner 的标量归约可与写入重叠，出生列表构造则必须后移；不能再直接照搬旧 pipeline 的提前完成方式。它只是一个内存与同步的实验选项，尚未实现，也不把记录载荷缩小等同于整个进程 RSS 的同比下降。

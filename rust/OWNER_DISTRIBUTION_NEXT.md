# Owner routing and integer hashing: next isolated experiment

The present `owner_for` is not a hash of `a XOR b` alone. For pair key `k=(a<<32)|b`, `k^(k>>32)=(a<<32)|(a^b)`, so the high `a` remains. In particular, `(a,a)` maps according to `a`, and `(a,b)` need not share an owner with `(b,a)`. A route change justified by the supposed symmetry would target a nonexistent bug.

A read-only count of initial adjacent pairs in the 4 MiB fixtures shows the current owner map balances **distinct keys** much better than physical positions. With W=4, English has 8,371 distinct pairs split 2,054–2,112 per owner, while its 4,177,990 pair positions split 844,577–1,361,805 (maximum/mean 1.304). Chinese has 290,930 keys split 72,238–73,088, and 1,711,753 positions with maximum/mean 1.060. At W=16 the position ratios are 1.850 and 1.109. Hot keys, not a collapse of `AA` keys into one bucket, explain much of the skew. Reassigning owners could distribute multiple hot keys more evenly, but cannot divide one key's posting append and adds work to every route calculation.

Three independent directions remain:

1. **Integer-key HashMap builder.** Compare the existing `std::collections::hash_map::RandomState` with cached `ahash 0.8.12` `RandomState` in one binary. Keep the current `owner_for` and all routes. Dispatch once for the whole training call to `train_impl<H: BuildHasher + Default + Clone + Send + Sync>`; `Owner.entries`, producer `Route.delta`, owner combined deltas, selected key maps/sets and frontier head/tail sets all use `H`. The main cost is a generic type parameter across the owner/route kernel and two compiled copies of that kernel. There is no per-key variant branch, second index or extra asymptotic memory. `ahash` is locally cached with its dependencies, is randomized by default, and supplies its own correct `Hasher` implementation, avoiding a custom byte-write fallback. It is an experimental comparison, not a claim that every corpus or CPU benefits. Its implementation can depend on CPU AES capabilities and compiler flags; neither implementation guarantees constant worst-case lookup time. Hash iteration order may change, but exact candidate order is explicitly frequency/key ranked; old/new delta sums are checked integer addition; birth-chain order need not be sorted except AA's selected list, which is sorted separately. Full oracle equality must still gate use.

2. **Sparse producer→owner routes.** Replace each producer's W route headers and each owner's W route scan with only active producer/owner pairs, plus an inverse directory built once per epoch. Expected work can approach O(active pairs + route entries) rather than O(W² + route entries), but routing now needs an owner-to-route lookup per emitted delta, or extra temporary indexing. A dense W-bit activation mask with compact active routes is a possible middle ground; setup and lookup costs may exceed saved empty scans at W=4. Persistent key/position lists remain unique. This changes the route interface and should be a separate experiment.

3. **Alternative full-pair owner mapping.** Avalanche the full 64-bit pair key before modulo W, then compare initial and update owner work skew under the same exact kernel. It changes no correctness property because each key still has one deterministic owner, and uses O(1) memory. It also changes route cost per occurrence, may worsen otherwise balanced fixtures, and does not remove a single heavy-key lower bound. The observed English skew is enough to motivate an offline routing distribution check, not enough to assume a speed gain.

The first experiment is the smallest measured test of **total hash work**, rather than field width or another scheduling protocol. Frozen `owned_grouped_inline` W4 4 MiB phase measurements indicate meaningful hash-heavy time: English owner initialization 0.0667 s, frequency reduction 0.1009 s and grouped birth fill 0.0534 s; Chinese 0.0864 s, 0.0937 s and 0.0276 s. Planning also performs selected-map lookups. These phase times include other work and do not measure hasher cost directly. The controlled experiment should report same-binary `--integer-hash std|ahash`, full trace, call/CPU seconds, train VmHWM and deterministic work counters at W1/W4 before deciding whether to retain it.

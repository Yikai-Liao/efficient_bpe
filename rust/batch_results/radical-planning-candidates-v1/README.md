# Exact BPE planning candidates: narrow corpus, cache reuse, and contexts

Three independent crates extend the frozen `owned_grouped_inline` trainer without changing exact greedy rule order. `owned_narrow` compares `u32`, `u16`, and automatic endpoint-corpus width. `owned_route_cache_reuse` keeps the same 4096-slot two-way route cache either for one batch or across the whole training call. `owned_context` groups correlated left and right neighbor updates through bounded per-producer context directories. The tested modes and CLI arguments are fixed in [modes.json](modes.json).

All final sources passed debug library tests (11/11 for each crate), strict all-target Clippy, and release builds. The `owned_narrow` tests were rerun after its final hot-path cast change. An oracle compared complete ordered merge traces and final tokens to a Python naive full recount: **438/438 valid runs matched**. Explicit `u16` rejected the `initial-alphabet-65536` case for both worker counts, as its documented ID bound requires; those **two expected rejections** are recorded separately. `u32` and `auto` handled that case. All 36 quick-screen calls matched native complete traces and fingerprints, and eight shared deterministic work counters agreed with frozen combo. See [checks.json](checks.json), [differential.json](differential.json), and [summary.json](summary.json).

The quick screen used EN and ZH continuous 256 KiB fixtures, 512 rules, one run per cell, CPU 5 for one worker and CPUs 0, 1, 2, 5 for four workers. Every call includes training initialization and finalization. The frozen combo binary ran in the same window; it predates the `call_cpu_seconds` field. Times below are full training-call seconds, with **n=1**, so they are diagnostic rather than a stable ranking.

`auto` chose `u16` on both quick fixtures, but its time differs from explicit `u16`; one run cannot separate mode-selection overhead from run-to-run variation. The layout also changes capacity, not only element width. On EN, 260,983 positions used `u32` endpoint capacity 262,144 (1,048,576 bytes) versus exact `u16` capacity 260,983 (521,966 bytes). The 526,610-byte difference is 521,966 bytes from element width plus 4,644 bytes from the `u32` spare slots. On ZH, 108,317 positions used `u32` capacity 131,072 (524,288 bytes) versus exact `u16` capacity 108,317 (216,634 bytes): 216,634 bytes from width plus 91,020 bytes from spare capacity. The incoming `u32` corpus capacities stayed 262,144 and 131,072 respectively during conversion. Thus the measured `u16` path is a **narrow-storage plus exact-allocation** comparison, not an isolated 2-byte-width effect. Training VmHWM also includes process startup and input parsing high water.

Reuse keeps cache hit counts nearly unchanged but sharply reduces initialization and final scans. With four workers, EN 4096-slot batch→reuse reduced cumulative initialized slot payload from 36,175,872 to 524,288 bytes and scanned slots from 1,130,496 to 66,307; ZH fell from 45,613,056 to 524,288 bytes and from 1,425,408 to 30,518 slots. EN `plan_seconds` fell from 0.0233 to 0.0178 s, and ZH from 0.0123 to 0.0064 s. Full-call EN W4 moved only from 0.0527 to 0.0504 s in this run; ZH moved from 0.0316 to 0.0232 s. The byte fields count cache payload initialized or allocated, **not measured DRAM traffic**. The reuse cache persists for the training call and adds touched-index/bitset storage; its `peak_route_cache_payload_bytes_upper_bound` is a reported payload bound, not process RSS. The measured versions also differ in replacement-phase state: batch mode resets `victim_way` to zero each batch, while reuse mode carries it across batches. This screen therefore does not isolate allocation and scan savings from that replacement-phase difference.

The context planner reduced the reported producer route-map update count through grouping. EN four-worker calls recorded 376,913 hits over 428,419 context lookups; 568,418 original updates mapped to 67,321 flushed route updates. ZH recorded 52,828 hits over 75,608 lookups and 100,226→30,004 updates. EN W4 `plan_seconds` changed from 0.0249 to 0.0169 s with a full-call change from 0.0600 to 0.0507 s. ZH W4 changed from 0.0071 to 0.0086 s and 0.0275 to 0.0351 s. The bounded context directory and entry-capacity payload reported for W4 is 37,728+301,824 bytes on EN and 203,472+524,288 bytes on ZH; it is not a complete RSS account. Context had no consistent net gain across these two inputs at this size.

`call_cpu_seconds` uses `CLOCK_PROCESS_CPUTIME_ID` over the full training call. Its ratio to `call_seconds` is average occupied cores, including stalls, not useful-computation utilization. All metrics, including CPU time, training VmHWM, actual requested/effective mode, widths, conversion time, cache scans, and context flushes, remain in [quick.jsonl](quick.jsonl). Phase fields can be nested and should not be summed indiscriminately. No 4 MiB or full performance matrix was run for these three candidates.

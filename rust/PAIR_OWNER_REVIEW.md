# Pair-owned counts and strict candidate selection: implementation review

**Status (2026-09-30):** [parallel_sharded.rs](src/ablation/parallel_sharded.rs) implements the first pair-owned prototype. Each persistent worker owns exact scalar counts and a heap for a disjoint hash partition of pair keys, while also retaining its own historical occurrence fragments. The coordinator merges owner candidate pages, assigns rule IDs, and controls phase barriers; it does not reduce per-position or per-key deltas. The implementation uses fixed contiguous initial-position shards, then retains new occurrences with the worker that produced them. It has **not** implemented AA run-prefix parity across shards: AA still gathers and sorts valid starts on the coordinator. It also has not implemented a sparse holder directory or epoch-tagged mailbox records. The separate `RELAXED` variant in [parallel_certified.rs](src/ablation/parallel_certified.rs) changes greedy rule selection and is not evidence for this exact prototype.

The read-only audit of the frozen first revision found no concrete candidate-loss or phase-ordering error. `held` contains every locally prefetched entry; `ReturnCandidates` restores every unselected entry, including the first conflicting candidate and unused page suffix, before delta reduction. The restored old score is a valid lazy upper bound because the next local `pop_best` compares it with the exact owner map before publication. All initial count producers finish before owners drain initial inboxes; all `Prepared` replies arrive after routing deltas and before `Reduce`; all `Reduced` replies arrive after drop sets are published and before `Apply`. The single in-flight epoch and these barriers make untagged mailboxes valid for this implementation. This is a source-level audit; tests and performance are reported separately.

The principal remaining costs are concrete: initialization broadcasts every owner's eligible-key set to all position workers for the second scan (rather than sending only to source holders), `Apply` makes each worker iterate every owner's retired-key set, costing O(WD) index probes per epoch for D retired keys, and each producer's routing creates W bucket vectors per batch. The eligible sets are released after `BuildIndex`, but their peak and the temporary initial count maps/mailboxes still matter. Owner scalar-map capacity can retain allocation for initial rare keys after `retain`, even though these keys no longer occupy the logical map. These are optimization targets, not exactness defects.

The `parallel_pair_owned_compact` ablation reuses that protocol and changes only the plan payload: each validated match stores a 4-byte start, while a 16-byte rule group stores the cumulative end, new ID, and two token lengths. `Apply` reconstructs `right` and `after` from the same lengths that passed `valid_pair` during the stable planning phase. The corpus is unchanged until all workers have prepared and owner reduction has finished, and certified match spans do not overlap, so the unchecked stores remain within the validated bounds. AA still uses the coordinator's globally sorted, left-to-right selected starts and checks adjacency against that full vector before creating its one group. The compact buffer excludes stale historical starts, but the source historical Vec is alive while its rule is being planned; on AA rounds, the global selected Vec and worker-local compact starts also coexist. Count start capacity, group capacity, and 12-byte new-edge capacity separately when interpreting peak memory.

## Current ownership and next-step refinements

Use a deterministic mix of the full packed `(u32,u32)` key to assign exactly one pair owner in `[0,W)`. Each worker has two private maps: its existing `pair→Vec<u32>` historical fragment map, and a `pair→u64` scalar frequency map **only for keys it owns**, plus one local strict heap. The coordinator stores rule metadata, token lengths, and at most W current candidate heads/pages. It has no global frequency map and never iterates all worker deltas. A hot pair's owner receives O(W) grouped scalar partials, while its position work remains on fragment workers. Dynamic producer ownership can skew a hot pair's fragments; the pair owner must not collect or concatenate the positions.

Initial position workers count every local pair and route one `(key,partial_u64)` per distinct local key directly to `owner_pair(key)`, then relinquish temporary count maps. Pair owners combine all senders with checked `u64` arithmetic and decide **global** `min_frequency`. The prototype publishes each owner's eligible-key set to all workers for the second parallel scan; sparse eligibility replies only to source workers are a future memory optimization. The coordinator receives W completion/status records, not `Σ_i K_i` counts. Public input validation remains serial, so initialization is **not yet fully parallel** end to end.

The simplest counterexample to local threshold filtering is `corpus=[0,1,2,0,1,2,0]`, two weight-1 pieces on different workers and `min_frequency=2`: each shard has `AB=1`, but global `AB=2` is eligible. A fresh-key regression is two weight-1 `XAB` pieces with `A=1,B=2,X=3`: initial `AB` beats `XA` on the lexicographic tie, and after `AB→Z` each worker creates one `(X,Z)` edge. Its global count is 2, though each producer sees only 1; local fresh-key filtering loses the next rule.

## Candidate pages: exact ordering without W round trips per candidate

At a completed epoch boundary, each owner validates stale heap entries against **its own exact map**, pops/leases its best `(frequency,key)`, and publishes that head or empty. The coordinator keeps a W-way merge heap ordered by descending frequency, ascending packed key. Owner ID is never a tie-break: deterministic pair ownership makes duplicate keys across owners an invariant error. For example, equal-frequency `(1,3)` and `(2,1)` assigned to different owners must select `(1,3)` regardless of which owner replied first. Leasing the published head before serving a later page prevents the owner from returning that same key twice.

At each epoch start, the coordinator concurrently requests a page of 32 candidates from every owner. When it exhausts one owner's page, it requests the **next** page from that owner only, not from all W workers. The owner pops/validates its local heap and holds popped entries in an epoch-local *lease*. The exact next global candidate cannot be chosen until an exhausted owner's next head (or empty reply) is known. Larger pages reduce requests but overfetch candidates and retain more lease memory, particularly when the prefix stops after one rule. Measure page size rather than tuning it to one dataset. The k-way merge costs O(W + B log W) coordinator comparisons for B accepted rules, plus owner-local heap work and O(W + page-refills) control exchanges per epoch. This removes a per-candidate **all-worker** barrier, though an exhausted owner's reply is still a genuine ordering dependency.

Take only the consecutive old-key prefix. On the first self pair or head/tail conflict after a nonempty prefix, stop immediately; do not skip to a lower-ranked key. The first self pair executes alone. The coordinator assigns fresh IDs in the accepted global order. A candidate page is a snapshot of old-key **exact** counts: no owner applies corpus deltas until selection is finished. A lazy old heap score may be an upper bound while being validated locally, but the owner must return the exact current score before that key can win. After batch commitment, selected leased keys are deleted. Every unselected leased key, including the stopping candidate and unused prefetched entries, must be returned to its owner's heap. Two restore timings are valid: before delta reduction, reinsert the old exact score as a lazy upper bound and require a strict local `pop_best` validation in the next epoch; or after reduction, reinsert its post-batch exact score if still eligible. Publishing the old score directly as a next-epoch **exact** candidate, or losing an unconsumed page entry, can change the next rule. Detect and discard duplicate lazy heap entries for a key already leased.

A small selection regression: make `AB` weight 5, `BC` weight 4, and `DE` weight 3 across several workers, with pairs ordered as shown. Once `AB` is accepted, globally next `BC` conflicts and the exact prefix must stop at length one; a page protocol that only sees one owner's candidates or skips a conflict would incorrectly include `DE`. Test equal-frequency keys on different owners and a stopping candidate whose count falls below threshold during the epoch; a restored old score may remain in the lazy heap but must be discarded by strict validation before it can win.

## Delta publication and eligibility

Position workers still plan all matches from one stable corpus snapshot. Each locally combines signed final-edge deltas by pair, partitions those **key-level** records by `owner_pair`, and sends one batch per target owner. The coordinator waits only for W worker *phase-complete/error* replies. Once all producers finished sending, it issues `ReduceEpoch(epoch_id)` to the same W threads in their pair-owner role. Each owner drains its bounded-to-one-epoch mailbox, combines **all** signed contributions for each key in `i128`, and changes its `u64` count once. Applying sender batches as they arrive can falsely underflow when positive and negative changes to a key cancel. The owner reports local maxima and errors only after all its key updates and heap repairs finish. No owner waits synchronously for a peer worker: phases are directed by the coordinator, avoiding a cycle when each thread is both producer and owner.

A current-batch fresh key contains an ID at least `first_new_id`; its final batch count is the sum over **all** producers. Only the owner can decide whether that global count meets `min_frequency`, then send retain/drop decisions to workers holding its provisional `NewEdge` records. With producer-owned fragments, a producer that emitted a positive fresh-key delta is a prospective holder; retain sender IDs or a compact holder directory. For an old key already below threshold and removed from the owner map, later negative deltas may be ignored: old-ID pairs cannot gain edges, because every newly emitted edge contains a fresh ID. A positive delta for such an absent old key is an invariant error. When a tracked old key falls below threshold, the owner deletes its scalar state and sends retirement to **every historical fragment holder**, not just workers that sent a delta this epoch. A broadcast retirement list is a simple first version but costs O(W × retired keys) worker lookups; a sparse holder list or small bitmask is the next optimization. Selected keys must end with exact frequency zero after all deltas; the owner checks this before publishing success.

Keep `Prepared`, `ReduceEpoch`, `Apply`, and next-candidate publication as explicit phases. Frequency ownership may be updated after all read plans and before corpus writes, as the current kernel does, but no next candidate may be dispatched for corpus planning until all writes and fragment retain/drop decisions have committed. The immutable-read barrier remains necessary even with `AtomicU32`; atomics prevent a Rust data race but do not make mixed pre/post-batch neighbor reads semantically valid. The current `Plan` is 16 bytes and `NewEdge` 12 bytes; these buffers and producer-local position maps remain in the next version. Pair ownership removes the coordinator delta map and global heap; it does **not** remove AA's O(M log M) gather/sort fallback or the W copies of token lengths.

## Failure and memory boundaries

If overlapping epochs or asynchronous routing are added later, use epoch IDs on cross-worker delta and verdict messages. Currently at most one epoch is in flight; coordinator barriers separate mailbox phases. Do not introduce a peer-to-peer blocking receive while a worker is performing its producer role. If any worker reports an error during plan or owner reduction, the coordinator drops worker handles; their `Drop` sends `Finish` and joins them without starting Apply or another candidate epoch. A partially updated private owner map is discarded with the run, never returned as a result. `std::sync::mpsc::Sender::send` is nonblocking for unbounded channels, so the present worker `Drop` pattern can drain its already queued finite command and join; a future bounded channel or peer acknowledgment changes that proof and needs an explicit shutdown path. Avoid a global mutex around all pair maps: it would restore the serial key reducer under a different name.

Account for `Σ_i K_i` producer fragment-map entries, `4Σ_i Vec::capacity`, owner map/heap entries (one copy per key), candidate page/lease buffers O(W × page size + B), per-worker delta map capacities, routed payload and mailbox high water, provisional new-edge buffers, W token-length copies, corpus conversion peak, and the AA coordinator vectors. Report all owners' update time and the slowest owner, not just their sum. A key hash may skew distinct touched keys even when positions are balanced. The exactness check is the complete ordered rule key/frequency/ID trace and final tokens against the serial reference; `position_visits` and `stale_visits` need not match.

# Producer-local old-pair aggregation followed by shared atomic reduction

Status: implemented in [owned_atomic_old](experiments/radical/owned_atomic_old/DESIGN.md); 17 Rust library tests and [85 complete oracle traces](batch_results/radical-atomic-old-gate-v1/README.md) pass. The text below records the protocol and measurement requirements; gate success is not a timing result. This is a separate experiment from pending owner entries. The control compares the **location of old-key reduction**, while keeping the same batched BPE certificate, corpus, fresh-key grouped birth path, hash choice, owner tables, and posting format.

## State and transition

Each permanent owner `Entry` uses `AtomicU64` for frequency in both modes. On the target 64-bit platform this should keep the 24-byte `Entry` layout, but the implementation must assert/report the actual size. During batch selection the coordinator removes selected entries and transfers their postings to the batch; it then stops structurally mutating every owner dictionary until all producer jobs join. Workers may read these dictionaries concurrently while planning. They never read a frequency to decide whether an occurrence is valid: corpus inspection and the existing selected-key certificate determine plans. Only old-key frequencies change during this interval. Fresh keys remain in per-producer owner-route maps, and no next selection occurs until corpus apply and complete fresh birth fill/publication.

The same binary should expose `--old-reduce owner|producer-atomic`, default `owner`. A call also reports the requested and effective modes. Lazy heap uses the requested mode. Eager heap with `producer-atomic` should explicitly fall back to `owner`, because eager refresh needs one final candidate per changed old key and would otherwise add a separate touched-set protocol. Both modes use the same `Entry<AtomicU64>`, producer route maps, direct-old owner reduction code, and temporary **fresh** combined map. The original staged combined-old path may remain an external context baseline; the causal comparison is owner vs producer-atomic in this binary. Do not include pending-entry or accumulator-reuse changes.

Owner control: after apply, each owner visits its producer route buckets. For an old key it looks up the Entry, uses `get_mut` and checked subtraction under exclusive owner access, retires immediately if below minimum, and never pushes an eager candidate more than once. Fresh records use the original combined grouped birth path. Producer-atomic: at the end of each producer's planning job, after its local map has aggregated all its occurrence deltas, it scans each `route.delta` with `retain`. For each old record with `head==MAX`, it looks up the shared immutable owner dictionary, skips a missing selected/filtered/previously retired key, and performs exactly one `fetch_sub(Relaxed)` for this producer/key. A retained Entry can be below minimum because another producer crossed the threshold, but its structure is still present until join. If `old>=minimum && old−delta<minimum`, this producer retains the old route entry as a unique **retirement marker**. Otherwise it removes the old route entry. Fresh entries stay in the map. `old<delta` is an internal error; a wrapping `fetch_sub` may already have occurred, so the entire private training call must join all jobs and return `Err`, never continue to another epoch or expose a result. A checked CAS loop could avoid the transient wrap but changes the measured protocol and should be a separate variant if needed.

After all planning jobs join and corpus apply finishes, each owner sees only fresh route entries plus at most one retirement marker for each old key. On a marker it verifies the current atomic frequency is below minimum, removes the Entry, and drops its posting. It does **not** subtract the marker weight again. It combines/counts/fills fresh births exactly like the owner control and publishes new candidates only after their posting-length checks. `retain` cannot return `Result`; the worker records a local error flag, stops further atomic actions after that flag, finishes the scan, and returns the error. Rayon results must all join before error propagation. The old record count must be captured before `retain`, since post-flush routes retain only retirement markers.

## Why the boundary is exact

Every changed old pair contains IDs below this batch's first fresh ID; every newly formed edge includes a fresh ID. Old frequencies therefore only decrease within this batch. The existing token-type certificate prevents overlapping selected non-AA matches; AA parity selects non-overlapping starts. The planner already suppresses duplicate neighboring old-edge deletion between adjacent selected merges, and sums `u64` piece weights in the producer-local route delta before any atomic call. The atomics change neither edge selection nor the amount decremented. For a valid key with initial `f≥minimum`, the `fetch_sub` operations are linearized in one order and all decrements have a nonnegative total residual. Exactly one operation can cross `minimum`; it leaves exactly one marker. A key absent from the shared dictionary was either selected or filtered/retired earlier and is skipped as in the owner control. No map insertion, removal, rehash, posting mutation, or heap refresh races with producer lookups. `Relaxed` suffices for the frequency arithmetic because the producer join separates all atomic updates from structural retirement and the next selection; no occurrence inspection relies on an inter-worker frequency observation. The owner must not be borrowed mutably or structurally modified until that join.

The precise error boundary matters. A malformed route with total decrements greater than an Entry's frequency eventually triggers `old<delta` in some atomic order; the private call then returns an error after join. Tests must not expect the owner table to be reusable after such an error. If the app later requires recoverable training state, use a checked CAS/update log and rollback or discard the whole trainer instance; this prototype only returns a result or an error.

## Expected work, risk, and measurements

Let `D_old` be old route records after per-producer aggregation, `R_old` old keys crossing the threshold, and `B_new` distinct born keys. Atomic mode issues at most `D_old` fetch-sub operations, not one per corpus occurrence. It still performs `D_old` owner-dictionary lookups and a `retain` scan. It moves only `R_old` old route entries into owner commit, but each producer's hash bucket capacity and the `W²` route headers remain allocated; the retained-marker trick does not itself save those bytes. Fresh combined/fill remains `O(B_new + birth records)`. Atomic updates can overlap with other workers' planning and remove old-key work from the owner critical path. Against that, RMW coherence, hot-key contention (up to W producers/key), false sharing among nearby `AtomicU64` Entries, extra dictionary probes, and `retain` work may outweigh the saved owner scan, especially at W=1 or with few old deltas. A lazy heap entry is still refreshed later on peek, not in the producer.

Record `old_route_records_before_flush`, `atomic_old_calls`, `atomic_old_hits`, `atomic_retire_markers`, `atomic_flush_seconds`, and `owner_old_updates`, plus fresh route/birth work, route capacity before and after flush, owner/fresh stage seconds, call CPU/wall time, and training VmHWM. Counts should be summed across jobs; capacity must not be presented as actual allocated bytes. The required comparisons are same binary/hash/heap/workers with identical complete traces and `actual_merges`, posting visits, stale visits, generated/stored birth records, batch widths, and final tokens. Directed tests need weighted adjacent selected matches, AA parity, selected-key absent lookups, two producers decreasing one key across the threshold, already-filtered keys, `u64` overflow/underflow error, and lazy heap tie refresh. Results on natural weight-two/min-two fixtures cannot alone characterize high-threshold retirement behavior.

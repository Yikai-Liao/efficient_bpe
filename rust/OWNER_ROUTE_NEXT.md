# owner 路由的下一轮实验

目前较有希望的基础是 `experiments/radical/owned`：每个 pair 的历史位置和频率只归一个 owner，位置扫描采用动态任务，所有规则保持串行贪心的严格顺序。`owned_probe` 与 `owned_counts` 已通过完整轨迹验证，但还没有足够的净速度收益支持默认组合。先用独立实现回答两个不同问题。

## 省去逐位置重新解码

稳定语料上的规划已经计算了每条最终出生边的 key。现有 owner 版为了只路由 4 字节位置而丢弃 key，写入后再次从语料恢复它，再对每个位置查目标哈希表。相邻规则可以同时产生两个新端点，但规划能从已选规则表得到这两个 ID；因此 key 本身并不依赖写入后才能确定，只有从位置恢复 key 的做法依赖写入完成。

`owned_grouped` 在每个生产者到 owner 的增量表中保留链头。更新值为 `{weight: u64, occurrences: u32, head: u32}`，仍占 16 字节；临时出生数组元素改为 `{position: u32, next: u32}`，占 8 字节。规划本来就要查一次 key 的增量表，在这里同时把新位置挂到链头。owner 汇总次数并分配列表之后，对每个生产者的每个新 key 查一次目标列表，再沿链复制位置。低于阈值的 key 可以整条链跳过。

它把出生填充的哈希查找次数从出现次数降为非空的 `(producer, key)` 组合数，并省去逐位置的两次语料读取及长度表读取。链顺序不必有序：普通非 AA 匹配互不重叠，AA 在选中后仍单独排序。永久索引还是每位置 4 字节；临时出生数组从 4 增为 8 字节，链访问也可能损失局部性，不能声称空间必然改善。归约仍 checked，局部链长和最终列表长度都与物理出现次数核对。

这一布局还允许后续把 owner 更新与语料写入并行，因为前者不再读取正在改写的端点；也允许各 owner 在自己的频率汇总结束后立即填充列表，省去两者之间的全局屏障。本轮先保留原阶段划分，隔离分组路由本身的效果。

## 避免最忙 owner 决定整轮耗时

位置扫描已经动态平衡，但频率和出生归约仍恰好只有 W 个 owner 任务。每个任务不能拆开，一个偏重 owner 就能拖住全轮。`owned_shards` 把逻辑 owner 数 S 与物理线程数 W 分开：生产任务仍恰好 W 个，永久 key 与位置仍只存一份，S 个 owner 任务交由 W 个线程动态领取。S=W 是同二进制控制项，2W 和 4W 用于判断更细分片的效果。

直接沿用每条候选扫描 S 个堆头会把选择成本变成 O(RS)。因此每批刷新 S 个精确堆头并线性建一个临时最大堆，选中某条规则后只刷新它所属 owner 的堆头。批内不修改频率，其他头保持有效；冲突时只丢弃临时前沿，不能把尚未执行的候选从真实 owner 堆移走。前沿空间 O(S)，选择附加工作 O(BS + R log S)，另计 owner 自己的过期堆项修复。R 为规则数、B 为批次数。

更多 owner 并不免费。当前生产者为每个 owner 留一个路由桶，桶头空间 O(WS)，每批遍历空桶的固定工作也为 O(WS)，全程 O(BWS)。增加 S 还可能降低局部性、增加小表分配。必须同时记录桶头字节数、owner 工作量最大值/总量、全调用时间及进程高水位；若分片变多只增加管理成本，就保留 S=W。未来几十核场景可能需要稀疏路由目录，但本轮不把该问题藏在配置默认值里。

## 工作量与判定边界

设 N 为实际语料位置数，不把 piece 权重展开。一次物理合并使活 token 数减少 1，最多产生两条最终相邻边，所以全程出生位置数为 O(N)，历史列表的总分配长度和选中后的总扫描长度也为 O(N)。过滤退休列表不会增加这项工作。空间探测另加一个受选中列表长度常数倍约束的扫描预算。

这不等于整个训练是线性时间：哈希操作是期望常数，优先队列仍有对数代价；AA 对历史列表排序可能贡献 O(N log N) 上界；候选前沿、空桶遍历、任务构建以及内存分配各有独立成本。若全是长度很小且相互依赖的单规则批次，增加线程不能创造独立的替换工作。自然语料、长 AA run 和串行依赖链需要分别报告。

每个新候选先跑定向 Rust 测试、完整轨迹 oracle 和 256 KiB quick。只有能解决明确疑问的候选才做有限较长输入测量；完整矩阵留到候选收敛。比较始终同时保留自身 1→4、最佳直接串行绝对耗时、原生并行参考及训练前后输出协议一致的内存口径。

## 尚未实现：大列表的分配与填充分开

增加 S 只能分散多个重 key。若大量出生位置都属于同一个 key，owner 顺序追加仍是整轮下界；增加哈希分片对此无效。分组路由保留了每个生产者的链长，因此可以让 owner 只做频率汇总、分配和范围划分，把这个 key 的位置填充重新交给多个生产者任务。

一种可审查的 Rust 实现不需要共享可增长的 Vec，也不需要并发修改它的长度：先按总次数分配 `Vec<u32>`，保持长度为零；从 `spare_capacity_mut()` 取得 `MaybeUninit<u32>` 区间，按各生产者的精确次数用 `split_at_mut` 切成互不相交的片段。每个任务只遍历自己的出生链并写自己的片段。所有任务成功 join、每片恰好写完之后才调用一次 `set_len(total)`。如果任何链校验失败，直接返回错误，长度仍为零，不能把未初始化的元素暴露为 `u32`。unsafe 只用于最后这一步，安全性依赖完整初始化的明确证明。

为避免大量短链的任务头和调度开销，应只拆超过阈值的大列表，小列表保持 owner 本地填充。可能通过 Rayon 嵌套任务在重 owner 内部释放并行工作，不必建立全局逐位置描述表。需要计入每 key 查找各生产者链的次数、额外任务描述和范围划分，而不是只算实际复制的字节。这是后续实验设计，当前 `owned_grouped` 尚未实现它，也没有性能数据。

另一项待定位的成本是未计入阶段的小表析构和统计遍历。最新 n=2 的 owned 四核中，完整调用减去不重叠的已计时阶段，英文还剩约 0.076/0.080 秒，中文约 0.095/0.093 秒；最终 owner 分别留有 336,700/454,899 个 key。这个差值不能直接称为析构时间。应先分别计入每批路由释放、最后的列表统计、owner 释放及线程池退出，且全部保持在完整调用计时内，再决定是否并行回收或改变小表布局。

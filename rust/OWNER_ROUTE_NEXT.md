# owner 路由的下一轮实验

本文前两项为已完成的设计记录。当前实验基础已更新为 `experiments/radical/owned_grouped_inline`；结果见 [并行报告](OWNER_PARALLEL_REPORT.md)。最初基础 `experiments/radical/owned` 的结构是：每个 pair 的历史位置和频率只归一个 owner，位置扫描采用动态任务，所有规则保持串行贪心的严格顺序。`owned_probe` 与 `owned_counts` 已通过完整轨迹验证，但还没有足够的净速度收益支持默认组合。先用独立实现回答两个不同问题。

## 省去逐位置重新解码

稳定语料上的规划已经计算了每条最终出生边的 key。现有 owner 版为了只路由 4 字节位置而丢弃 key，写入后再次从语料恢复它，再对每个位置查目标哈希表。相邻规则可以同时产生两个新端点，但规划能从已选规则表得到这两个 ID；因此 key 本身并不依赖写入后才能确定，只有从位置恢复 key 的做法依赖写入完成。

`owned_grouped` 在每个生产者到 owner 的增量表中保留链头。更新值为 `{weight: u64, occurrences: u32, head: u32}`，仍占 16 字节；临时出生数组元素改为 `{position: u32, next: u32}`，占 8 字节。规划本来就要查一次 key 的增量表，在这里同时把新位置挂到链头。owner 汇总次数并分配列表之后，对每个生产者的每个新 key 查一次目标列表，再沿链复制位置。低于阈值的 key 可以整条链跳过。

它把出生填充的哈希查找次数从出现次数降为非空的 `(producer, key)` 组合数，并省去逐位置的两次语料读取及长度表读取。链顺序不必有序：普通非 AA 匹配互不重叠，AA 在选中后仍单独排序。永久索引还是每位置 4 字节；临时出生数组从 4 增为 8 字节，链访问也可能损失局部性，不能声称空间必然改善。归约仍 checked，局部链长和最终列表长度都与物理出现次数核对。

这一布局还允许后续把 owner 更新与语料写入并行，因为前者不再读取正在改写的端点；也允许各 owner 在自己的频率汇总结束后立即填充列表，省去两者之间的全局屏障。本轮先保留原阶段划分，隔离分组路由本身的效果。

## 避免最忙 owner 决定整轮耗时

位置扫描已经动态平衡，但频率和出生归约仍恰好只有 W 个 owner 任务。每个任务不能拆开，一个偏重 owner 就能拖住全轮。`owned_shards` 把逻辑 owner 数 S 与物理线程数 W 分开：生产任务仍恰好 W 个，永久 key 与位置仍只存一份，S 个 owner 任务交由 W 个线程动态领取。S=W 是同二进制控制项，2W 和 4W 用于判断更细分片的效果。

直接沿用每条候选扫描 S 个堆头会把选择成本变成 O(RS)。因此每批刷新 S 个精确堆头并线性建一个临时最大堆，选中某条规则后只刷新它所属 owner 的堆头。批内不修改频率，其他头保持有效；冲突时只丢弃临时前沿，不能把尚未执行的候选从真实 owner 堆移走。前沿空间 O(S)，选择附加工作 O(BS + R log S)，另计 owner 自己的过期堆项修复。R 为规则数、B 为批次数。

更多 owner 并不免费。当前生产者为每个 owner 留一个路由桶，桶头空间 O(WS)，每批遍历空桶的固定工作也为 O(WS)，全程 O(BWS)。增加 S 还可能降低局部性、增加小表分配。必须同时记录桶头字节数、owner 工作量最大值/总量、全调用时间及进程高水位；若分片变多只增加管理成本，就保留 S=W。未来几十核场景可能需要稀疏路由目录，但本轮不把该问题藏在配置默认值里。

## 工作量与判定边界

设 N 为实际语料位置数，不把 piece 权重展开。一次物理合并使活 token 数减少 1，最多产生两条最终相邻边，所以全程出生位置数为 O(N)，历史列表的总分配长度和选中后的总扫描长度也为 O(N)。过滤退休列表不会增加这项工作。空间探测另加一个受选中列表长度常数倍约束的扫描预算。

这不等于整个训练是线性时间：哈希操作是期望常数，优先队列仍有对数代价；权重定位对 P 个 piece 起点做二分，初始化和实际替换合计 O(N) 次查询带来 O(N log P) 项；AA 对历史列表排序可能贡献 O(N log N) 上界；候选前沿、空桶遍历、任务构建以及内存分配各有独立成本。若全是长度很小且相互依赖的单规则批次，增加线程不能创造独立的替换工作。自然语料、长 AA run 和串行依赖链需要分别报告。

每个新候选先跑定向 Rust 测试、完整轨迹 oracle 和 256 KiB quick。只有能解决明确疑问的候选才做有限较长输入测量；完整矩阵留到候选收敛。比较始终同时保留自身 1→4、最佳直接串行绝对耗时、原生并行参考及训练前后输出协议一致的内存口径。

## 大列表的分配与填充分开：已完成独立实验

增加 S 只能分散多个重 key。若大量出生位置都属于同一个 key，owner 顺序追加仍是整轮下界；增加哈希分片对此无效。分组路由保留了每个生产者的链长，因此可以让 owner 只做频率汇总、分配和范围划分，把这个 key 的位置填充重新交给多个生产者任务。

一种可审查的 Rust 实现不需要共享可增长的 Vec，也不需要并发修改它的长度：先按总次数分配 `Vec<u32>`，保持长度为零；从 `spare_capacity_mut()` 取得 `MaybeUninit<u32>` 区间，按各生产者的精确次数用 `split_at_mut` 切成互不相交的片段。每个任务只遍历自己的出生链并写自己的片段。所有任务成功 join、每片恰好写完之后才调用一次 `set_len(total)`。如果任何链校验失败，直接返回错误，长度仍为零，不能把未初始化的元素暴露为 `u32`。unsafe 只用于最后这一步，安全性依赖完整初始化的明确证明。

为避免大量短链的任务头和调度开销，应只拆超过阈值的大列表，小列表保持 owner 本地填充。可能通过 Rayon 嵌套任务在重 owner 内部释放并行工作，不必建立全局逐位置描述表。需要计入每 key 查找各生产者链的次数、额外任务描述和范围划分，而不是只算实际复制的字节。该设计随后在独立 `owned_scatter` 中实现；[实测归档](batch_results/radical-fused-scatter-v1/README.md)显示 4 MiB 上已触发，但没有明显完整调用净收益。`owned_grouped` 本身仍保留原路径。

另一项待定位的成本是未计入阶段的小表析构和统计遍历。最新 n=2 的 owned 四核中，完整调用减去不重叠的已计时阶段，英文还剩约 0.076/0.080 秒，中文约 0.095/0.093 秒；最终 owner 分别留有 336,700/454,899 个 key。这个差值不能直接称为析构时间。应先分别计入每批路由释放、最后的列表统计、owner 释放及线程池退出，且全部保持在完整调用计时内，再决定是否并行回收或改变小表布局。


## 正在分开检验的规划优化

更新路径已经推进到 owner 本地连续归约/填充，以及直接扣减旧 key。下一处大成本是规划阶段逐位置查询小规则表和路由增量表。两者用独立原型检验：共享的小规则表只含本批最多 256 个 key；有界路由缓存由每个生产者私有，命中时先在缓存中累计，再成组写入现有 owner 路由。前者最多 512 个 16 字节槽，整个批次一份；后者 4096 个 32 字节槽意味着每生产者 128 KiB，64 个生产者约 8 MiB，不能称为零成本。

缓存不随词表或语料位置数直接增长，但每批初始化和最终扫槽多出 O(BWK) 固定工作；K 为每生产者槽数，B 为批次数。碰撞只影响命中率，不改变精确结果。出生位置仍使用原 8 字节临时链节点，缓存段驱逐时以尾节点接上已有链头，不能遗失重复驱逐之间的片段。小规则表比较完整 key，线性探查有容量上界，不能把短指纹相等当作 pair 相等。两项还需要独立测量再决定整合。

更激进的跨批推测不能只建立空间冲突 DAG：执行高频 AB 后可能产生比旧候选 CD 更高频的新 ZZ；旧 BC 也可能被 AB 替换降为零。AA 还受整条 run 的奇偶选择约束。可探索的窄子问题是先完成当前规则的精确增量，用稀疏端点覆盖层规划经真实频率验证的下一规则，失败时只丢计划、不回滚共享语料。它仍保留贪心选择依赖链，并增加受预算约束的临时状态；当前未实现，不声称能实现无屏障的通用精确训练。

有界缓存的后续方向是跨批复用分配、仅 flush 本批触及槽，以及按已选历史位置数的上界限制活动槽数。它们都只是待测假设；高命中率未带来提速，不能仅凭累计清零字节数就断定原因。缓存槽内的 born 链索引必须在本批输出释放前全部清空，错误或展开时不能复用仍指向旧数组的槽。另一项独立设计见 [并行端点位宽](ENDPOINT_WIDTH_NEXT.md)：在整轮 ID 域有界时尝试 16 位原子端点，明确转换峰值与超域回退，不把串行 CF16 的高位拆分方案误当成简单的 u16 ID 限制。


## 权重查询的复杂度补项

当前 owner 内核的初始化对每个初始物理边查询一次权重，非 AA 只对实际匹配、AA 只对奇偶筛选后的真实替换查询一次。若初始边数为 E0、实际替换数为 M，调用总数 E0+M=O(N)，但每次 `pivots.partition_point` 是 O(log P)。因此不能仅由位置历史为线性大小推出整个规划 CPU 线性。这里 N 按物理位置计，不展开 piece 权重；P=1 的连续输入中该项为常数，不是当前测量的非线性瓶颈。

可以单独研究 O(W) 的最近 piece 区间缓存，命中直接取权重，最坏仍是二分。若 piece 很密，可用 N 位起点位图加每 512 位置一个 u32 前缀 rank，以最多 8 次 popcount 定位：载荷约 N/8+N/128=0.1328N 字节。只有在替换原 pivots 且 P≥约0.0332N 时，才不大于原数组的 4P 字节；若两者同时保留，它就是额外内存。边界取整、数组容量、索引构建和权重数组要另计。此方向尚未实现，不作为本轮提速结论。


## AA 排序的最坏界：尚未实现的独立方向

选中 AA 时仍需按物理位置恢复整条 run 的左到右奇偶选择。当前历史 posting 不保证全局有序，因而使用比较排序，最坏 O(H log H)；全程历史位置线性并不能消掉这个项。位置是 u32，适合另试原地 MSD radix partition：每层计数 256 个桶，用置换环把元素放到互不重叠桶区间，再递归处理下一字节。固定 32 位至多四层，不复制整个 H 长数组；顺序递归的计数/游标栈为常数大小。桶区间可以安全拆成不重叠可变 slice 后再并行，但任务阈值和每个并发任务的计数数组必须计入内存。

这是整数域带来的最坏界改进候选，不是已获得的性能结果。单桶高字节、近乎有序输入以及短 posting 可能使常数比标准排序更差，初版应保持同二进制 sort_unstable 控制，以长 AA、乱序历史位置和自然语料的 AA 子阶段作小型判别。若排序之外的工作主导完整调用，不应为漂亮的排序数字合入主线。当前未实现，也未安排完整矩阵。

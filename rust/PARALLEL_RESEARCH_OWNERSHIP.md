# Ownership and exact priority for parallel BPE training

This is a design exploration, not an implementation decision or a speedup claim. The fixed semantic contract is the ordered merge rules (pair, weighted frequency, fresh ID) and final tokens; `position_visits` and `stale_visits` are implementation counters and may differ between correct algorithms. The current snapshot prototype chooses the exact global maximum weighted pair (frequency descending, packed pair ID ascending), visits that pair's historical positions, performs left-to-right non-overlapping replacements, and updates affected counts and histories. A single continuous input must remain continuous. Its coordinator still selects plans and reduces occurrence records.

## Exact maximum: what must be owned

Two distributed layouts are meaningfully different.

**Position-owned, replicated pair counts (YTTM-like).** Worker `s` owns positions in a corpus region and local `count_s(pair)` plus a local historical list. The exact count is `Σ_s count_s(pair)`. Its local maximum is **not** enough to find the global maximum: with two workers, `A=60+60` can beat `B=100+0` and `C=0+100`, even though neither worker reports `A` as its local best. A central candidate queue can hold safe upper bounds and query only plausible contenders across workers; YTTM does this with O(W) count checks. A long stream can be split by physical position only if boundary matches, `AA` parity and endpoint ownership are handled exactly.

**Pair-owned scalar state, position-owned occurrence fragments (hybrid candidate).** Deterministically map each packed pair key to one owner. That owner stores its exact `u64` frequency, a local strict heap, and a directory of corpus shards with historical records. Each corpus shard keeps its own ordered `pair→positions` fragments and its endpoint memory. During initialization, corpus workers scan disjoint start ranges and send locally combined `(pair, weighted_count)` records directly to pair owners; no coordinator iterates all positions. The pair owner sums its inbound records, validates overflow, and builds its heap. The position fragments stay where they were scanned. After an epoch's updates are fully applied, each pair exists in exactly one owner's table, so the maximum of the W owners' exact local maxima is **provably** the global maximum under the total `(frequency, reversed packed-key)` order. The coordinator handles W scalars, not all pair keys or occurrences. Local heaps may be lazy only if each owner validates its top against its own current table before reporting.

For one selected rule, the owner identifies active position shards and broadcasts the key and fresh ID; each active shard scans its own indexed fragment in physical order. A continuous corpus needs boundary summaries: for `AA`, communicate run parity across neighboring shards; for adjacent `ABAB`, correct the later match's left context to the preceding new token. The resulting selected spans must be disjoint before concurrent endpoint writes. Each shard then locally combines signed frequency changes and routes one message per touched pair to that pair's owner. The owner combines **all epoch deltas** for a key in `i128` before changing its `u64` count; applying sender messages in arrival order can falsely underflow on a temporary fresh edge created in one shard and removed in the next. If the implementation retains historical position lists, their records remain ordered per source shard, and a cross-shard assembly needs explicit shard order. A direct live-index rebuild may omit stale records if it still produces exact next-rule counts and replacements. The epoch closes only when all active shards and touched pair owners have acknowledged it. Then local maxima are exact again.

This hybrid is an inference from owner-computes and vertex-cut systems, not a cited ready-made BPE implementation. It should distribute the O(occurrences) work of a hot pair while keeping the pair owner's state update near O(active shards + touched keys), but requires extra maps, routed messages and exact boundary logic. A pure pair-owner layout that also stores and updates one giant position Vec for a hot pair would recreate a serial hotspot and may add copying.

## Reducing synchronization without relaxing the result

The simplest exact protocol has one global rule at a time. Barrier cost is real, but eliminating a barrier by reading a not-yet-updated local maximum is incorrect. A cheaper exact maximum within that protocol is possible: cache each pair owner's validated top at the coordinator and update a tournament tree only for owners touched by this rule plus the winner's owner. Untouched owners retain the same exact top. This changes O(W) max comparison to O(touched owners × log W) after their acknowledgments; it does **not** eliminate the necessary completion condition. The owner directory or routing messages identify touched owners.

A more ambitious candidate is YTTM-style **upper-bound certification** while one non-self rule is in flight. For `AB→Z` with fresh `Z`, any final `(L,Z)`, `(Z,R)`, or `(Z,Z)` edge maps injectively to a pre-merge `(L,A)`, `(B,R)`, or `(B,A)` boundary respectively. Weighted new frequency cannot exceed that ancestor old-pair count. Since `Z` is larger than all old IDs, each ancestor also wins our lexicographic tie against its descendant. Old-pair counts only decrease, so an unreconciled pre-merge count is a safe upper bound. If an exact independent candidate beats **every** possibly affected ancestor upper bound, the unseen new keys cannot outrank it. This supplies a certificate for the *next choice* rather than a relaxed queue. `AA` needs a separate self-run proof; serial fallback is safer initially. Concurrent application is another proof obligation: adjacent rules can edit one boundary even if their selected pairs do not share tokens, so independent sequential-rule updates require ordered execution or a separately proved batch-end update. YTTM's whole-word worker ordering supplies the former property for its data model; our continuous endpoint array does not get it for free. See the exact source evidence in [the implementation note](PARALLEL_RESEARCH_IMPLEMENTATIONS.md).

The certificate appears to extend to a **consecutive prefix of old-key candidates**, not merely two rules. Consider each next candidate in the exact pre-batch order and stop at the *first* key that conflicts with any selected non-self rule; do not skip it to take a lower-ranked key. A pair `(C,D)` conflicts with selected `(A,B)` when `C=B` or `D=A`, the two possible shared-token orientations. Nonconflicting old-key pairs keep their counts because existing-ID pairs can only lose edges when one of their operand tokens is consumed. After several disjoint selected pair types, an edge containing current-batch fresh IDs `Z_i,Z_j` still descends from exactly one pre-batch boundary `(right(P_i),left(P_j))`; an old/fresh edge descends from `(L,left(P_j))` or `(right(P_i),R)`. Its weighted count is at most that one ancestor's pre-batch count. That ancestor conflicts with at least one selected rule, remains as an unreconciled upper bound, and precedes the fresh descendant under packed-key ties. Thus an exact next old-key candidate that beats all frozen affected bounds also beats all unseen descendants. This is a deduction under fresh monotonically increasing IDs, exact candidate counts, unchanged weighted boundaries, and no self rule in the prefix; it is **not** a completed implementation proof. A stale heap entry may be used as an upper bound, never as the selected candidate's exact score. Refreshing an affected old bound downward before its descendant count is known would break the certificate. A self-pair rule ends the prefix unless a separate bound is proved.

Batching such a prefix requires reproducing the effect of its rules in ID order and retaining enough state to compute every selected rule's frequency and final tokens exactly. It does **not** require preserving transient historical records. For example, many separate `AB` and `CD` pieces can make those rules the first two safe choices, while `ABCD` and `ABCX` create `(Z_AB,C)` in both pieces after `AB`; `CD` then removes only the `ABCD` occurrence. The archived historical-list trainer may later visit two records, one stale, whereas a batch implementation that builds only the final live index may visit one. Both are correct if the ordered rule triples and final tokens agree. This difference is an opportunity to reduce work. It matters only when comparing implementation counters or reusing archived history-dependent code; net deltas alone are insufficient for that archived index's internal invariants, not for the fixed semantic contract.

### Direct batch-end adjacency update (conditional design)

The conflict test above gives selected non-self rule types `S` with `heads(S) ∩ tails(S) = ∅`. Any two selected occurrences sharing a token would make that token the tail of one selected type and the head of another; therefore **all live selected occurrences are token-disjoint**, including repeated `AB` in `ABAB`. Since earlier rules in this prefix consume none of a later selected type's tokens and cannot create an old-ID pair, each selected rule's exact frequency remains its pre-batch frequency. Assign fresh IDs in certified rule order, then inspect a *single immutable pre-batch snapshot* to plan all selected occurrences. This argument depends on the prefix certificate above for the rule choices; disjointness alone does not certify a greedy prefix.

For a selected occurrence `(A,B)→Z_i`, read up to two live tokens on either side in the snapshot: `X,L,A,B,R,Y`. A missing neighbor or a zero separator does not make a counted edge. Define `left_selected` when `(X,L) ∈ S`, and `right_selected` when `(R,Y) ∈ S`. These tests are exact adjacency tests: a selected match immediately to the left must end at `L`, and one immediately to the right must start at `R`. The final left neighbor is `Z_j` at `X` if `left_selected`, otherwise `L`; the final right neighbor `R*` is `Z_k` at `R` if `right_selected`, otherwise `R`. With the corpus piece's weight on every nonzero edge, emit these signed changes:

1. Delete the internal old edge `(A,B)`.
2. If `R` is nonzero, delete the old edge `(B,R)` and add the **final** edge `(Z_i,R*)` at this match's start position.
3. If `L` is nonzero and `left_selected` is false, delete `(L,A)` and add `(L,Z_i)` at `L`'s start position. If `left_selected` is true, the left match owns this shared boundary via step 2, so emit neither change here.

Every old edge touched by a match is deleted once: the internal edge by its own match, a boundary between adjacent selected matches by the *left* match, and a boundary against an unselected token by its sole neighboring match. Each replacement edge is likewise emitted once and already uses its batch-end IDs. All other edges remain unchanged. Thus the batch can route only final signed pair deltas and final live occurrence starts to pair owners; it need not construct short-lived `(Z_i,A_j)` records or preserve archived stale visits. Apply combined signed deltas before updating an owner's `u64` count, with overflow validation. The physical corpus update still writes each disjoint selected span once, using its assigned `Z_i`; the rule/frequency/ID sequence and final tokens must equal the serial trainer, while position-visit and stale-visit counters may differ.

For `ABAB` with the one rule `AB→Z`, the first match removes the middle `(B,A)` and emits `(Z,Z)`; the second sees `left_selected` and does not touch that boundary again. For `ABCD` with `CD→Z_1` selected before `AB→Z_2`, the `AB` match removes `(B,C)` and emits `(Z_2,Z_1)`; the `CD` match skips its selected left boundary. The same result holds when their rule order is reversed, with IDs assigned accordingly. A short exhaustive check of 34,236 ordered non-self rule sets over words of length at most six (alphabet size four, up to three rule types) found the direct final tokens, pair counts, and per-rule frequencies identical to sequential replacement. This is a sanity check, not a proof of the prefix-selection certificate or a performance result. A piece weight multiplies every local edge delta, and zero separators terminate both adjacency and weight propagation.

The intended phases are: publish a certified ordered rule prefix and immutable corpus/index snapshot; let position-owning workers validate and plan their own live occurrence fragments (including cross-shard neighbor reads); finish **all** snapshot reads; then perform disjoint token-span writes and route worker-local pair deltas/position fragments to owners; finish the owner update before the next global selection. There must be no coordinator pass over every match. A physical shard boundary may bisect a token span or its two-neighbor context, so ownership and snapshot lifetime need an explicit implementation proof. Distinct token spans can still share packed bitmap words or nibble bytes; concurrent native writes need word-aligned ownership, per-shard metadata, or another race-free scheme. Historical occurrence lists must not double-plan a live start, and final occurrence fragments must be assembled in physical order when the next algorithm depends on it. `AA`, any head/tail conflict such as simultaneous `AB` and `BC`, uncertified priority bounds, invalid or stale indexed positions, and arithmetic overflow require their separate checks or a serial fallback. The hoped-for benefit is fewer temporary edges and fewer rule barriers, at the cost of extra local neighbor reads, routed distinct keys, and a potentially short certified prefix; none has been measured yet.

## Work, traffic, and questions to measure

Let `W` be workers, `R_t` indexed positions of the winning pair in round `t`, and `D_t` distinct `(source shard, target pair owner, pair key)` updates. The hybrid aims for parallel position work roughly `R_t/W` when balanced, routed count traffic O(`D_t`), and global choice O(`W`) or O(touched owners × log `W`). It cannot remove the sequential dependence between arbitrary successive greedy rules, and it must not hide O(`R_t`) work inside the coordinator's planning or index assembly. Count updates can commute and combine; `AA` selection and boundary context cannot be arbitrarily reordered. A new index may discard stale positions as long as counts and final replacements remain exact.

The first evaluation should report coordinator CPU time, owner CPU skew, messages/bytes, distinct keys per owner, hot-pair position distribution, barrier wait, RSS, and equality of ordered rules with frequencies and final tokens against the archived serial Rust trainer. Visits and stales should be reported separately as algorithm-dependent work measures. A certified-prefix prototype also needs its prefix-length distribution, first-stop reason (conflicting key, self-pair, exhausted queue, or uncertified bound), number of exact candidate-count queries, and temporary index bytes; a frequent length-one prefix cannot amortize synchronization. Compare a single long random string, long `AA` runs, adjacent `ABAB`, many weighted pieces, and high-uniqueness new keys. On a dual-socket Xeon, place corpus shards by first touch and bind workers to their shard's socket before judging NUMA scaling; GraphIt's documented NUMA choices are workload dependent. The current 6-vCPU, one-NUMA-domain pilot cannot settle dual-socket scaling.

The native certified-prefix probe now establishes nontrivial batch widths on real text, so the next structural experiment should combine batch-end adjacency construction with local count/position ownership. Pair-owned scalar heaps and position-owned fragments remain competing implementations of the aggregation layer. Grouped flat-reducer and capacity-shrink patches remain deferred local ablations. No architecture is designated a performance winner until exact traces, memory use and multicore measurements support it.

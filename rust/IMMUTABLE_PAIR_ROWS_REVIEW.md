# 以较新 token ID 建只出生一次的 pair row：审查草案

结论：**不可变 key 目录、可变 Entry**在语义上成立，但不宜直接把每个 `max(a,b)` row 固定给一个 owner。较有价值的最小实验是保留现有 owner 路由，先量每批新键按较大 ID 分组的 row 大小分布及 lookup 次数；只有小 row 占优势时，稀疏自适应 row 才可能抵消重建索引和查找成本。此处尚未实现或测得提速。

**单次出生证明。**初始相邻 pair 在初始扫描全部已知。每次改写只把两个旧 token 合成一个本批新 ID；所有新形成的邻接边至少含一个本批新 ID。故 pair `(a,b)` 若在第 `e` 批首次出现，此后没有改写能再增加它的出现，旧 Entry 的频率只会因覆盖旧边而下降。两个本批 fresh ID 相邻、或 AA 生成 `(Z,Z)`，仍由本批提交完整生成；row 归属 `t=max(a,b)`，同批末归约后可封存。必须保留当前 selected 候选连续前缀、AA 奇偶、weighted `u64` 频率、堆同频 key 次序以及 batch apply→birth fill→发布的屏障。`row` 不可变仅指 key 集合和索引位置；Entry 的频率、posting、存活状态仍可变。退休可置频率零并释放 posting；旧 heap candidate 按 Entry 当前频率校验。零频条目不能再次复生。

**键编码与空间。**在完整 32-bit token ID 域中，partner 需 32 位，方向再需 1 位，不能无条件塞进一个 `u32`。可为 `(t,p)` 与 `(p,t)` 设两条有序 partner 数组，`(t,t)` 只存一次；或用一个 `u64` descriptor。64 位平台当前 `Entry` 是 24 B，若分别存 4 B partner 和连续 Entry，理论 payload 约 28 B/历史 key；直接 `Vec<(u32,Entry)>` 因对齐一般是 32 B，另有 posting heap 和容器容量。dense CSR 可给每 ID 约 4 B offset（双方向为 8 B）并让历史 records 连续；每 row 各用 `Vec` 则是约 24 B header/ID 加许多小分配。上界中，实际 merge 次数不超过初始非零 token 数（更紧的界须扣除非空 piece 数），初始边数和全程 birth occurrence 总量都为 `O(N)`，因此历史不同 key 与 dense row 数均为 `O(N)`，不是无界随 epoch 复扫。不过这仍可能比当前活跃 key 数 `K` 大得多；HashMap 可复用退休桶，永不复用历史 row 槽则累计到 `O(B_total)`。RSS 还包含 retained stale postings 和 allocator 碎片，不能仅比 payload 字节。

**反例与查找代价。**合法输入可由大量各含一个不同初始 ID 的单 token piece 组成：所有 ID 稠密且已使用，但没有任何 pair；每 ID 一个 24 B row header 会额外花 `Θ(N)`，而现有 owner map 无 key。密集 offset 数组仍至少 `Θ(N)`，稀疏 row 目录才避免它。相反，一个高频 `(A,B)` 合成 `Z`，在不同邻居 `Cᵢ` 前出现，可让 row `Z` 含 `Θ(N)` 个方向键；该 row 若归单个 owner，归约/填充串行且可能比现有按完整 pair 分散 owner 更斜。此 row 后来只剩一个活键时，保留全部死亡 record 又浪费空间并拖慢查找。由于同 row 不再出生新键，可以在 `dead≥half` 时只复制 live records 重建独立分配的排序 row；每次复制至多当前规模一半，几何和小于初始 row 大小，所以全程迁移 `O(B_total)`，但重建瞬时新旧两份共存。全局 CSR arena 若不能归还单个 row 的旧区间，就不享有这项释放收益；堆候选必须按完整 key 重新查找，不能持有重建后失效的索引。小 row 线扫成本 `O(s)`；排序后二分为 `O(log s)`，大 row 的每次旧边减频都额外付这个比较/随机访存成本。只用 fingerprint 的静态 hash 会误认碰撞，必须比较完整 partner+方向；可靠的静态字典也需建表空间、构造失败路径和发布屏障。`B_total≤O(N)` 不能推出 `B_total≈K` 或 row 很小。

**可实现的稀疏变种。**按出生批收集 `(rowID,orientation,partner,count,posting)`，所有 producer join 后对同 row 排序/去重并一次发布；初始 row 同样在初始归约后封存。维护仅非空 row 的全局目录：少量 row 可排序二分，较多时用整数 rowID→row 索引 map；每 row 对小键组线扫、大键组二分，超过实测阈值才考虑精确静态 hash。若仍需 W owner 并行，可以把高 fanout row 按 partner hash 分片，目录记录每 row 的非空 shard；小 row 保持单 shard。固定 W 份 dense 目录会把 header 放大到 `O(W·(L+R))`，应避免。分片不能复制 posting，堆和旧键更新须路由到唯一 shard；同批跨 fresh ID 的 pair 也必须只入 `maxID` 所属 row 的一个 shard。另一保守实验是**只改 row 内索引**，保持现有完整 key owner 映射，在每 owner 建稀疏 row；这样可隔离 lookup 布局，但每 owner 仍有 row 目录/小容器成本。全局 row 目录若给每 `(ID,owner)` 留一个固定槽会占 `O((L+R)W)`，改用二级稀疏索引或 handle 又增加哈希、指针追踪和额外分配，不能直接预期省内存。

优先采样 `row` 大小、每 row 后续旧键查找次数、非空 row 数、`B_total/K_peak` 和每 owner 的 row 出生量；这些量决定是否值得从现有 HashMap 迁移。要比较实际内存，需记录完整训练 VmHWM、row header/descriptor/Entry/posting 分项以及构建时旧表和新 row 同时存在的峰值；一次性迁移不能漏掉双份 live records。当前无须改变已冻结 trainer。

# Parallel BPE design and exactness conditions

The three piece modes share a global heap ordered by descending weighted frequency and ascending packed pair key. `serial` runs the same shards on the coordinator; `broadcast` sends every selected rule to every persistent worker; `owner` sends it only to workers recorded in that pair's owner mask. Each worker owns complete input pieces, including their zero separators, and applies the rule to its own historical positions in left-to-right order. The coordinator waits for every dispatched worker's count delta before selecting the next rule. A single long piece therefore has one worker in these modes. Old-ID pairs can only lose occurrences; every pair newly created by a merge contains that round's fresh ID. Initial counts and each worker's reported new keys establish a conservative owner mask. Stale owners can waste work but cannot hide a live occurrence. `broadcast` and `serial` allocate no owner directory. If `owner` requests more than 128 workers, it falls back to broadcast and reports `owner_fallback_broadcast=1` rather than shifting beyond the `u128` mask.

The continuous-corpus modes keep one shared atomic u32 endpoint array and do not insert shard boundaries. `occurrence` is the reference implementation: for each selected pair it scans only that pair's historical positions and uses a sparse overlay of earlier writes to plan exact sequential contexts. `occurrence_snapshot` first validates those positions against a stable snapshot in parallel, then selects replacement spans on the coordinator, then applies disjoint endpoint writes in parallel. Both retain persistent threads; neither scans or clones the entire corpus each rule.

`occurrence_adaptive` uses the same snapshot path for large rules and a coordinator-local path when a rule's historical occurrence count is below `1024 × actual_workers`, or when there is only one worker. The fixed-grain ablations `_256` and `_4096` differ only in that threshold. The local path scans historical starts in physical order, reading and writing the current endpoints as it goes; this directly reproduces the sequential trainer's overlap handling and context, including `AA` and `ABAB`. Its count deltas and new occurrence records still pass through the same global reducer, so this is a dispatch and planning ablation rather than the direct-update packed trainer. It sends no worker messages and crosses no worker barrier for those rounds; when only one worker is requested, it does not spawn a redundant thread. Historical count is a dispatch proxy rather than the count of live matches; the latter is unknown until validation. No dataset name or corpus-specific rule chooses the threshold. `serial_rounds`, `serial_visits`, `parallel_rounds`, `actualbarriers`, `adaptive_grain`, and `worker_threads_spawned` make the routing observable; `serial_seconds` covers the local scan and endpoint updates, while `reduce_seconds` continues to cover the shared reducer.

The snapshot selection relies on these invariants:

1. Historical position lists are nondecreasing. Initial lists come from a left-to-right corpus scan. For a fresh pair, replacements are processed in physical order and append positions at the chosen match or its immediate left boundary; a later match's left boundary cannot precede the earlier match's start. The snapshot implementation checks order within and between worker chunks and returns an error if it fails.
2. A snapshot-invalid occurrence cannot become a valid occurrence of the selected old-ID pair during that rule: replacements only remove old tokens and introduce a fresh ID. If the selected pair is `AB` with `A != B`, two snapshot-valid matches cannot share a token; shared-token overlap would require `A == B`. For `AA`, each run of valid edges is greedily matched at alternating starts, reproducing left-to-right non-overlapping replacement. Overlapped historical records count as stale visits.
3. For a selected match, its right neighbor is unchanged in the snapshot because matches to its right have not yet been applied in sequential order. If the previous selected match ends exactly where this one begins, its left neighbor is the previous match's new token at the previous start; otherwise the left neighbor is unchanged in the snapshot. This correction reproduces intermediate edge updates as well as final counts. In `ABAB`, the first match removes the old `BA` edge and creates a temporary `(new,A)` edge; the second removes that temporary edge and creates `(new,new)`. Thus the old edge is removed once, and historical temporary occurrences retain the same order and stale-visit behavior as the sequential trainer.
4. Selected spans are disjoint. A worker writes only the left start and the right token's endpoint positions inside its assigned span. All validation finishes before any apply write; all apply replies arrive before global reduction and the next rule. `AtomicU32` makes concurrent corpus access data-race-free, and the channel barriers make the next snapshot observe completed writes. In `occurrence_snapshot`, checked indexing and private `get_unchecked` indexing run through the same validated entry; each unchecked access is preceded by a boundary or accepted-plan proof. The older `occurrence` reference retains checked atomic indexing regardless of the `Bounds` option.

The public input validator rejects malformed separators, IDs, pivots, lengths, and weights, and checks that the total initial weighted adjacency fits `u64`. Pair counts remain within that total as merges remove adjacencies; signed per-rule deltas use `i128`. Exactness is conditional on the stated historical-order and phase invariants and on no external mutation of the private corpus. The tests cover random continuous strings, long `AA` runs, adjacent `ABAB` matches across worker chunks, uneven pieces, extreme valid weights, checked/unchecked access, and the same rules, final tokens, actual replacements, visits, and stale visits as the sequential core.

`init_seconds` includes index construction and worker startup. `merge_seconds` includes all rules, barriers, and global reduction; final extraction is outside it. The snapshot mode reports `validation_seconds`, `serial_select_seconds`, `plan_seconds` (both phases), `apply_seconds`, `reduce_seconds`, and `sync_seconds` (time waiting for replies, contained within validation/apply). It reports worker dispatches and work seconds, plus actual `size_of` and peak vector-buffer bytes for selected positions, the coordinator's 4-byte `Valid` vector, and its 24-byte `Plan` vector. Workers release their references before replying: the selected historical list is released after validation and the valid-list buffer after selection, so neither overlaps the apply phase. The shared atomic corpus is 4 bytes per original position, with additional pair maps, heap entries, worker result maps, and allocator overhead not captured by buffer fields. Process RSS remains the measure of total memory.

The global rule barrier and the snapshot mode's serial selection can dominate when rules have few occurrences, even with many cores. The adaptive mode removes both phase barriers for small rules, but the frequency and occurrence-list reducer remains serial. `sync_seconds` is contained in validation/apply time and must not be added to them. The current 6-vCPU KVM host is one NUMA domain; it cannot establish dual-socket Xeon scaling. On a real multi-socket machine, the shared atomic corpus may incur remote-memory traffic depending on first-touch placement. NUMA-aware allocation, worker affinity, and a reduction tree are future experiments, not properties of this implementation.

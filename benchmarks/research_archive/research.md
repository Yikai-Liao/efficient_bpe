# 初期源码审计与文献调研归档

本记录保存初期源码检查、文献对应和原始测量。后续已完成更公平的[共同核心比较](../bpe_core_comparison/REPORT.md)、[多版迭代与并行实测](../bpe_core_comparison/evolution/REPORT.md)，并建立[Rust 基线](../../rust/README.md)。涉及后续计划、候选方案和复杂度口径时，以这些更新文档为准。归档脚本仅将路径改成相对本仓库定位；原始结果不作改写。

研究对象：efficient_bpe，提交 `7bfbc63`。调研日期：2026-09-29。

判断：就已核对的代码及早于项目的文献而言，更接近独立重现已有高效思路，而不是已经证明了独特的新算法贡献。作者已明确说明项目系独立完成；这里比较的是技术路线与早先文献，不涉及照搬判断。项目具备值得保留的工程设计，尤其是“pair 的具体出现位置索引＋连续数组＋两端长度定位＋延迟清理”；但这些核心方向在 1999—2017 年的 Re-Pair 和项目之前的 YouTokenToMe 中已有实质先例。不能由比 HF 的某条实现路径更高效，推出超越此前最佳算法。

最有辨识度的具体设计是 v1 的“不可变原字符串＋每位置一个字节的双端长度表”。这不是与先例完全相同的编码；目前也没有找到与它逐细节一致的实现。但是，它以 255 字符上限换取紧凑、直接的访问，尚缺乏与既有紧凑 Re-Pair 布局在相同能力范围内的完整时间/内存比较，因而只能确认设计价值，不能确认新的领域贡献。u8 限制可以在不扩大长度元数据的条件下解决；本文验证了两种具体布局，较省空间的一种来自对已有 Re-Pair 位图方案的适配。

本次读取两个 Python 实现、评测 notebook、Git 历史和语料；做了本地运行、剖析、随机差分检查和独立布局原型。项目源文件未修改，实验保存在本目录。README 所链接博客的域名当前无法解析，未把无法取得的博客内容作为依据。

**1. 项目已经实现了什么。**

[v1 初始化](../../ebpe.py#L224)把规范化语料保留为不可变字符串，为每种 pair 保存 `array('I')` 具体位置，另用 `array('B')` 存 token 长度。合并后，token 两端保存长度，邻居可由长度直接定位，不移动语料。邻接 pair 的计数及时递减，位置列表允许留下过期项；堆顶失效时重新入堆，需要时整理位置。`preproc_idx` 对相同 token 的重叠出现从右向左处理。

[v2](../../ebpe_v2.py#L98)先统计独立词及频率，再将每个唯一词放入语料一次，用频率权重计数。语料数组存 u32 token ID，token 的字符长度集中在 `token_len`；按词频排序，用 `freq_pivot/freq_info` 找位置的权重。具体位置使用 u64。这已经取消了 u8 长度表，但改变了内存布局，并不是“保持原长度表容量”的解决办法。v2 的保存、加载、encode、decode 等仍是空方法，定位是训练原型。

v1 的输入单元是 Unicode 字符，不是 UTF-8 字节。所谓 255 上限是一个 token 最多覆盖 255 个原始字符位置。

**2. 本地证据。**

环境：Linux x86-64，Intel Xeon Gold 6140 虚拟 CPU，CPython 3.12.13，tqdm 4.70.1。语料为仓库 `data/train_BPE.txt`，7,056,124 文件字节、2,547,540 字符。训练参数：`vocab_size=10000, min_freq=15, compress_threshold=0.3, single_char=False`。因此目标是约一万个多字符词条，不能直接当成其他库包含初始字符的 vocab_size=10000。

独立进程、固定 PYTHONHASHSEED=0、各三次运行：

| 版本 | 时间中位数 | 进程峰值 RSS 中位数 | 输出 |
|---|---:|---:|---|
| 原版 v1 | 7.977 秒 | 144.63 MiB | 10,000 词条 |
| 只改变长度表初始化方式的临时版本 | 7.843 秒 | 125.09 MiB | 词表 SHA-256 完全相同 |

原版 `array('B', [1] * N)` 会先创建 N 个 Python 指针的列表；临时版本使用 `array('B', [1]) * N`。这消除了约 19.44 MiB 的瞬时指针列表，实测峰值下降约 19.54 MiB。时间差较小，不据此宣称稳定速度提升。[复现脚本](./v1_bench.py)和[原始结果](./v1_bench.json)。峰值包含解释器、字符串、字典等整个进程，不是单个数组大小。

一次独立 cProfile 运行中：初始化累计 6.20 秒，合并累计 5.22 秒，选最高频 pair 累计 0.38 秒，总计约 12.05 秒；剖析本身增加耗时，因此不与上述非剖析时间相加比较。结论是先优化初始化和合并，堆不是当前主要热点。

初始相邻 pair 总数 2,028,451；不同 pair 共 283,102 种，频率达到 15 的只有 21,029 种。现实现先为所有 pair 分配位置数组，之后再过滤，初始化期间存在大量最终不用的小对象。长度表本身仅 2.43 MiB，规范化字符串约 4.86 MiB，说明仅缩小长度表无法解释或消除一百多 MiB 的整体内存。

按 v1 原有标点边界拆出 236,021 个非空片段，唯一片段 150,873 个。片段字符数从 2,264,472 降至 1,594,728，减少约 29.6%。这是加权去重能减少的物理片段字符数，不是整体 RSS 或时间减少比例。哈希表、权重和边界也有成本。原版 `replace_punc` 创建了 `set(lines)`，却仍然 join 原来的 lines，并未去重。

正确性检查：

- v1 在保留其从右向左重叠规则的参考实现下，通过 2,000 个随机小语料的逐轮 pair/频率对照。
- v1 对 `['a' * 512] * 4` 训练可复现 `OverflowError: unsigned byte integer is greater than maximum`。
- v2 在不触发长度上限的 1,000 个随机小语料中未发现逐轮 pair/频率差异。
- v2 在 `max_piece_length=2`、输入 `aba` 时，先学习 `ab`，之后仍学习已经不存在的 `ba`。原因是旧 pair 的减频被放进了“新 pair 是否超长”的条件里。旧邻接边消失必须减频；新边能否进入候选是另一件事。[问题位置](../../ebpe_v2.py#L361)。临时版本修复此条件并用边界写替代整段清零后，通过 5,000 个随机语料的逐轮对照，覆盖长度上限 2、3、4、8 和近似无限，以及多个最小频率。[检查脚本](./v2_fixed_check.py)。

这些检查没有覆盖全部前后缀、特殊 token、字母表裁剪和持久化组合；不构成 v2 产品级兼容性证明。

**3. 与现有开源实现相比，优势具体在哪里。**

以下为源码结构比较，不是跨库速度排行榜。预切分、初始字符/字节单位、重叠方向、同频 tie-break、长度上限、词表大小口径未统一前，速度倍数没有足够解释力。

| 实现 | 训练组织方式 | 与本项目的关系 |
|---|---|---|
| Prezza 等人的 Re-Pair（2017） | 扁平文本、全局位置数组、延迟同步、高低频队列；位图与按块跳距提供 O(1) 邻居访问 | 是比 HF 更直接、也更强的算法和紧凑存储先例。需计入文本、位置数组和队列的全部内存。见 [论文](https://arxiv.org/html/1704.08558v1) 与 [作者源码](https://github.com/nicolaprezza/Re-Pair/blob/ffb411d8ce9c1232980ec67bee7e678c0b88fd5c/internal/skippable_text.hpp)。 |
| YouTokenToMe | 加权唯一词、具体 occurrence 索引、数组内链、重复字符 run 压缩、高低频队列；分词片段并行及受依赖约束的提前一轮流水线 | 在项目之前已实现许多原本可能以为尚缺的优化，包括训练并行。不能以 occurrence 索引或按片段并行作为相对它的新贡献。见 [固定版本源码](https://github.com/VKCOM/YouTokenToMe/blob/f4162d846057a3118222ca04a01b84297eb8a8db/youtokentome/cpp/bpe.cpp)。 |
| subword-nmt | 唯一词及频率，pair→词索引；只在相关词中替换并更新邻接统计；候选统计剪枝 | 增量计数和倒排索引已有；你的具体位置索引避免重新扫描整词。见 [learn_bpe.py](https://github.com/rsennrich/subword-nmt/blob/master/subword_nmt/learn_bpe.py)。 |
| fastBPE | C++、token ID、每词链表、pair→词集合；在连续计数数组上扫描最大 pair | 你的堆避免每轮全候选扫描，扁平位置布局也更紧凑；其词去重和 C++ 常数开销已有优势。多线程代码在 apply 路径，不能据此称训练主循环并行。见 [fastBPE.hpp](https://github.com/glample/fastBPE/blob/master/fastBPE/fastBPE.hpp)。 |

HF 的当前主干已进入 v1 RC 迁移，旧的 `tokenizers/src/models/bpe` 路径已经移动。上表核对的是 2026-09-23 的 `bbccb0513ff9afda385ca5c85c66eddb1318cfc7`，不是搜索引擎缓存里的旧目录。[官方当前说明](https://github.com/huggingface/tokenizers)。

对 HF 的具体潜在改进可以表述为：让某轮处理成本更接近“实际受影响的出现次数”，避免额外与“被扫描词的当前长度、移动的 Vec 元素数”成比例。这在长片段、长 token 或一个词多次命中时更有价值；在很短的预切分词上，Rust 的缓存局部性、少分配和批量处理可能让它的常数更好，需要测量。

YouTokenToMe 的节点含 `val/prev/next/seg_len`，通常占 16 字节，但对应的是连续相同符号的 run；位置记录含两个 u64，通常也占 16 字节。它未必比本项目省内存，却已具备具体位置更新，不能把它归为扫描整词的弱基线。其自配对按 `floor(run_length/2) × word_frequency` 计分，而本项目初始统计包含重叠的相邻对；二者不能直接要求 merge 序列相同。Prezza 的一个实际布局包含约 2N 字节文本、0.25N 字节位图/跳距、约 4N 字节位置数组，另有队列等开销；它与本项目的 Unicode 字符串及词表对象仍需统一输入和功能后比较。

**4. 文献对原创性判断的影响。**

1999 年 Larsson 与 Moffat 的 Re-Pair 已给出最频 pair 替换、出现位置组织、局部更新和专用优先结构，并讨论整体线性时间与空间的实现。[原论文 §2.3](https://avadeaux.net/larsson.dogma.net/dcc99.pdf)。这足以说明“避免每轮全语料扫描”早有算法先例。

2016/2017 年 Bille、Gørtz、Prezza 的 Space-Efficient Re-Pair 更直接：位置表、延迟整理、按有效频率与列表长度之比触发同步，以及利用合并留下的空位存双向跳转信息，都与本项目的思路很接近。其 §3.3 给出摊还分析，§4.1 解释如何在空位内部编码长度、在常数时间跳过空隙。[论文全文](https://arxiv.org/html/1611.01479v1)。因此，`compress_threshold`、数组替代链表和“内部空位存跳转”都不能仅凭本项目声称首创。

2017 年 Practical and Effective Re-Pair Compression 进一步给出实用的紧凑布局与位置数组方案，报告包含文本在内约 `(1.5+ε)n` 个 machine words 的工作空间。这里是机器字，不是字节，而且计算模型、输出形式及去重规则与 NLP tokenizer 不完全相同，不能直接拿其系数与本项目长度表的 1 byte 比较。[论文 §3](https://arxiv.org/html/1704.08558v1)。

2023 年 A Formal Perspective on Byte-Pair Encoding 用链表、出现位置及优先队列分析接近线性的训练，给出 `O(N log M)` 的算法论证。[论文 §4](https://arxiv.org/html/2306.16837v1)。其 M 是合并次数，并包含其自己的候选队列设定；本项目堆里保存所有达到阈值的候选，不能直接照搬 `log M`，更稳妥的是写 `log P`。

本地 Git 记录显示 v1 的首次提交是 2023-05-03；这早于上述 ACL 论文的公开 arXiv 版本，但晚于 Re-Pair 系列多年。提交日期可以记录你的开发时间，不能单独证明公开优先权，也不能抹去较早的相关工作。

本次核对的 YouTokenToMe 提交 `f4162d8` 日期为 2023-03-29，Prezza 实现 `ffb411d` 日期为 2017-04-06，均早于 v1。原创性判断主要依据这些更早的具体先例，而不是拿 2024—2026 年的工作倒推你在 2023 年不新颖。相对某些后来论文更早地写出类似优化，不自动意味着相对整个领域的优先权。

更近的研究为下一步提供参照，而不作为否定当年原创性的依据：

| 工作 | 实际推进方向 | 对本项目的适用边界 |
|---|---|---|
| [Rpair / BigRePair，SPIRE 2019](https://users.dcc.uchile.cl/~gnavarro/ps/spire19.5.pdf) | 先分解为重复片段字典和片段序列，再分别运行 RePair | 能利用跨词的重复结构，但切分约束改变候选，不保证同一全局 greedy grammar；并行主要在解析阶段。 |
| [Re²Pair，ESA 2024](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESA.2024.78) | 递归 prefix-free parsing 降低超大重复语料的工作空间 | 属于可扩展的 RePair 风格压缩；不能称为与原始全局 BPE 完全相同。其 RePair 步骤仍单线程。 |
| [RLZ-RePair，CPM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.CPM.2026.5) | 在参考串及 RLZ phrase 表示上维护全局 pair 频率，避免完全展开目标语料 | 更接近保持全局最高频 greedy 规则；作者也明确提到同频顺序、相同符号覆盖方向可能导致 grammar 差异。单线程实验限于高度重复 DNA，不能外推普通自然语言收益。 |

RLZ-RePair 提示，比“每个唯一词只存一次”更进一步的方向是共享不同词、文档之间的重复子串，并对 source/phrase 边界增量修正。它比单纯把 Python 热循环改写成 Rust 更有研究空间，但该基本路线本身也已有先例；自然语言、代码语料的重复率与短片段约束可能让其额外索引得不偿失。[作者代码](https://github.com/rvarki/RLZ-RePair)。

较新的 BlockBPE（2025）研究 GPU 上的并行编码，其输入已经包含学习好的 merge table，并且改变了 regex 预切分。它不能直接作为“保持完全相同训练语义的并行训练”解法。[论文](https://arxiv.org/html/2507.11941v1)。

此外，你在 v1 `word_count` 和被注释的删除零频中间 token 代码中，注意到了词表中间项不再实际使用的问题。这与后来的 [Scaffold-BPE](https://arxiv.org/abs/2404.17808) 和 [PickyBPE](https://aclanthology.org/2024.emnlp-main.925/) 的问题意识有关，但目前没有相应完整训练/推理语义和模型实验。能说看到了一个有价值的问题，不能据此认定已经完成那些论文的贡献。

**5. 时间与空间复杂度的下一步。**

设 N 为原始输入字符数，U 为加权去重后实际保存的字符数，K 为合并规则数，P 为活跃候选 pair 数，R 为实际执行的 occurrence 合并次数。每次实际合并都会减少一个活跃 token，所以 `R≤U`。正确维护位置列表时，每次合并只产生常数条邻接变更，总位置记录创建量可控制为 O(U)。因此，固定宽度 token ID、常数成本邻居定位、合理摊还清理和堆的组合，可以把核心训练做到接近 `O(U log P)`，另加原始读取/去重、排序、词表展开等成本。

这是目标分析，不是对当前所有代码路径的无条件上界。必须另算：

- v1 字符串切片、拼接、哈希成本。长度上限解除后，不能再将任意长字符串处理视作 O(1)。
- v2 对每次合并后的整个 span 清零的成本 `Σ length(merge occurrence)`。链式增长可到平方级；平衡增长也会反复写同一内部区域。
- v2 频率查找中的 `freq_pivot[freq_i + 1:]` 数组复制。bisect 的查找是对数级，不代表含切片的表达式是对数级。
- 将每个中间 token 展开成完整字符串的总字符数 D。长链情况下 D 也可能为平方级。需要长期保留所有展开字符串时，这是输出表示本身的成本；否则可保存 `(left_id,right_id,length,rank)` 规则，按需展开。

最先应修改 v2 的整段清零。[现代码](../../ebpe_v2.py#L353)可在其“所有无效内部槽为零”的不变量下变成四次写入：

```python
corpus[pos_y - 1] = 0
corpus[pos_y] = 0
corpus[pos_x] = new_token
corpus[pos_end - 1] = new_token
```

先清两个被吞掉的边界，再写新边界；顺序保证某一侧长度为 1 时也正确。不要仅删掉清零循环而留下旧端点。此改动不要求新内存，已在临时差分版本里验证。

针对连续向一个 token 并入字符的合并原语微测，长度从 1,000 增至 8,000 时，原循环从 0.069 秒增至 4.33 秒；四次边界写从 0.0062 秒增至 0.045 秒，符合去除平方级重复写入的预期。这仅隔离测量一个操作，不是完整训练器的加速倍数。[脚本](./microbench.py)与[结果](./microbench-results.txt)。

去重应在不可跨越的预切分边界内进行，并保留权重。直接丢弃重复行会改变 pair 频率。v2 的 `split()` 与 v1 的标点规范化不是同一语义，不能直接比较两者耗时来证明算法进步。

进一步减少堆的 log 因子可以参考 Re-Pair 的频率分层/桶式结构，但加权去重后的频率一次可能跳变很多；若还要求特定的同频排序，桶内也需维护顺序。这不是简单替换 heapq 即得到 O(U)。本地剖析里选 pair 约占 3%，暂不应优先复杂化这一部分。

**6. 工程常数和峰值内存的改进顺序。**

| 改进 | 原因与约束 |
|---|---|
| 数组直接重复初始化 | 已实测去掉约 19.5 MiB 峰值；v2 的 `array('I',[0]*N)` 同样有中间列表。 |
| 初始化先计数，再仅为达到阈值的 pair 建位置 | 本语料 28.3 万候选仅约 2.1 万保留，可减少小数组分配；代价是多扫描一遍。首次扫描的计数字典仍占空间。需保持初始 pair 只会减少等不变量，不能对可重新累加的键盲目丢弃。 |
| 位置索引池化/分块 | 用连续的 occurrence 存储和小描述符替代每 pair 一个 Python 对象；按有效位置数量做清理。 |
| v2 在分片内用 u32 offset | U<2^32 时每条位置从 8 字节降为 4 字节；大语料用天然边界分片，不允许静默溢出。加权总频率仍建议 u64。 |
| v2 不保留低于 min_frequency 的初始位置数组 | 现代码过滤了 pair_freq，却为全部 pair 保留 pair_pos。只在旧 pair 不会重新获得新出现的条件下可安全删掉。 |
| 去掉 bisect 的切片 | 使用 `bisect_right(freq_pivot, pos, lo=freq_i+1)-1`。现有外层 `pos>=next_pivot` 后的 `pos<freq_pivot[freq_i+1]` 分支永远不成立。 |
| 新 pair 累加使用紧凑 buffer | v1 的临时 list、v2 的 list→u64 array 转换都有 Python int/指针与复制开销；直接 array、arena 或原生 Vec 应分别测量。 |
| 将最热的 occurrence 更新放进 Rust/C++ | pair 用两个 u32 或打包 u64，频率用 u64，避免每个位置构造字符串/tuple；Python 保留 API。迁移时不能悄悄改变 tie-break、字符单位、同串不同合并路径的 token 身份。 |
| 关闭 v2 无条件 show_corpus | 训练末尾构造完整输出列表并 join/print，会增加时间和峰值；该项应受调试选项控制。 |

选择 v1 和 v2 路线需要明确：v1 保持原字符串＋1 字节边界信息，v2 以 4 字节可变 token ID 语料避免热路径字符串操作。后者可以不保留整份原始字符串，但总内存优劣要连同唯一词字典、位置数组、词表一起计算，不能仅看一个字段。

**7. 精确并行训练。**

最可靠的第一版是“全局串行选 pair，同一轮按独立片段并行合并”：

```text
全局频率表及确定性的最高优先级 pair
        ↓ 分发 pair、输出 token ID、rank
各线程只修改自己的完整片段/分片
        ↓ 返回局部频率差分和新出现位置
归约差分，更新全局候选，进入下一轮
```

可以并行的包括读取/预切分、初始计数，以及所选 pair 在独立词/段中的应用。这里的训练仍有 K 轮依赖；后期 pair 出现次数变少，应设置任务粒度阈值回到串行，避免屏障和调度成本超过合并本身。YouTokenToMe 和 HF 都已有按词分片的并行，不能把这个基本结构当成新贡献。

YouTokenToMe 还有更值得学习的流水线：全局协调者最多提前发布一条尚未完成的规则。若上一条是 `x+y→z`，候选属于被影响的 `y,*` 或 `*,x`，或者上一条是 self-pair，则等待。原因是未受影响的旧 pair 计数保持稳定，新 z 邻接 pair 的计数受对应旧邻接 pair 的计数约束；利用此上界可以在满足依赖条件时提前选择，而不是随意批量合并。见 [bpe.cpp 1121—1169 行](https://github.com/VKCOM/YouTokenToMe/blob/f4162d846057a3118222ca04a01b84297eb8a8db/youtokentome/cpp/bpe.cpp#L1121)。

作者压力测试用 `DETERMINISTIC_QUEUE` 固定同频顺序，将 8 线程 fast 版本逐规则与朴素 serial 版本对照。本次编译其测试（补编译参数 `-include cstdint`，未改源码），运行 `base 10` 的 10 个小样本均通过。默认构建不启用该同频排序，因此不能宣称默认输出与任意固定 tie-break 串行实现完全一致；大规模性能及默认同频一致性未测试。移植到本项目还需重新核对加权频率、长度限制、边界位和最小频率条件下的上界，不能把已有测试直接视为移植正确性证明。

CPython 常规构建中的 Python 循环不能靠线程池获得理想 CPU 并行。进程池若传递或复制完整 Python dict、set、字符串，会破坏省内存目标。应优先原生线程，共享只读规则和频率协调结构，语料分片单写者所有权，线程局部使用有上限的差分 buffer，而不是每线程复制完整 pair 字典。

不能直接把单条 position 列表随意分成几段就并发执行现有 merge：`aaaaa` 要保持一致的重叠配对方向，`abab` 同时变成两个 `ab` 时，共享邻接边必须只结算一次。若必须分割一个超长片段，需先确定不重叠 occurrence，再明确每条受影响边的归属，分阶段更新并修复跨分区边界。这比按天然片段切分更复杂，适合第二阶段。

多 pair 批处理也不能仅凭出现位置不重叠就视为等价。一次合并生成的新候选可能比本来准备批量执行的其他 pair 更频繁。只有额外证明优先级和依赖不会改变，才可保持原始贪心训练序列；独立训练多个 shard 后合并词表属于不同算法。

**8. 在不扩大长度表的条件下突破 255。**

优先考虑已核对的方案：活跃起点位图＋按块跳距。每 64 个原始位置用一个 u64 存起点是否活跃，再用一个 u32 存跨越全空块的长跳距。相邻两个起点的距离就是 token 长度；末尾常驻一个哨兵。合并时只删除右 token 的起点，并在新空隙首、尾的全空块保存跳距。短距离通过当前或相邻位图 word 的置位位置得到；长距离直接读跳距，不扫描零串。原生固定字宽模型下，前驱、后继和合并均为 O(1)。

长度元数据精确为 `12 × ceil((N+1)/64)` 字节，渐近约 **0.1875N 字节**，低于原 N 字节长度表；N<2³² 时 u32 跳距足够。更大位置范围改用 u64 跳距后约 **0.25N 字节**。这是边界元数据的大小，不包含原字符串、token ID、occurrence 索引和词表，也不是完整训练器的 RSS 承诺。很短的输入有按块取整开销。

这个方案改编自 [2017 年作者实现的 skippable_text](https://github.com/nicolaprezza/Re-Pair/blob/ffb411d8ce9c1232980ec67bee7e678c0b88fd5c/internal/skippable_text.hpp)。它不需要每个长 token 的溢出哈希表，也不要求把原来每位置的 u8 整体扩大为 u16/u32。关键不变量是：每个全空块只属于一对相邻活跃边界之间的 gap，两个 gap 不会争用同一个跳距槽；合并后的旧跳距可以残留，因为查询只访问当前 gap 的首、末全空块。

[独立原型](./blocked_bitmap_proof.py)通过 359,945 次随机及定向合并，最大实际长度 65,536，其元数据含哨兵共 12,300 字节。另一位 agent 编写的[独立核查](./compact_layout_independent_check.py)又对 12,740 次合并逐次检查全部活/死位置及双向邻居，均通过。`prev/nxt` 只对活跃起点有定义，过期 occurrence 必须先用 `alive()` 拒绝。Python 位操作与函数调用的常数不一定优于直接 u8 索引；完整训练集成及原生性能仍未测。

并行时，即便两个 token 不相邻，只要清位落在同一 u64 内，非原子读改写就有竞争。需按位图 word 分配写入所有权或使用原子清位；原子位图本身仍不能解决并发相邻合并时跳距和邻居关系的一致性。最简单的布局是让分片边界按块对齐、片内由单个线程修改。

还有两种备选，分别取更小空间和更接近 v1 的访问形式：

方案 A：只保存 token 起点的分层 bitset。合并时删除右 token 的起点位；前后置位位置之间的距离就是长度。底层 N bits，加每 64 个字一层的非空摘要，总量约 `N/8 × (1+1/64+1/64²+…) ≈0.127N` 字节。它取消了 255 上限，且比现有 N 字节更少。查询/更新是 O(log₆₄ N) 层访问，适合原生实现；不能只给平面 bitset 然后无界扫描长零串。本次未实现和测量这一方案。

方案 B：在原 N 字节数组中区分边界和内部数据，保留固定机器字范围内的常数时间读写。独立验证原型在 [layout_proof.py](./layout_proof.py)。一种便于证明不会误认过期位置的编码如下：

| 字节值 | 含义 |
|---|---|
| 0 | 无效内部槽 |
| 1 | 长度为 1 的 token，起点和终点相同 |
| 2…63 | 短 token 起点，值就是长度 |
| 64…125 | 短 token 终点，长度＝值−62 |
| 126 | 长 token 起点 |
| 127 | 长 token 终点 |
| 128…255 | 内部长度数据，每字节低 7 bit 有效 |

长度至少为 64 时，在起点后 5 个旧槽存 u32 长度，在终点前 5 个旧槽反向镜像存一份。两组数据及边界最多占 12 个既有位置，必然装得进长度至少 64 的 token。长度数据都≥128，永远不会被误认成起点或终点。

```text
长 token 原有的 L 个槽位：
[126][5 个长度字节] …… 内部空槽/旧数据 …… [5 个长度字节][127]
```

合并时先清除左 token 的旧终点与右 token 的旧起点，再写新起止边界，长 token 则更新两份长度。旧的内部长度数据可以保留，因为其标记不可能被当成活跃边界；无需清整段。方向读取必须封装成 `start_len` / `end_len`，原版直接比较 `seg[i]==len_a` 的代码需要同步改用这些访问器。

该编码让短长度的直接路径从 255 缩为 63，但不会降低可支持的最大 token 长度；64 以上走 5 字节解码路径。原仓库该次训练的最大 token 长度为 22，因此这份负载不会触发长路径；长文本负载需要另测。u64 长度可用每端 10 个既有槽，最长支持到所选位置类型的上限，不是无条件数学意义的无限长度。

原型经过 60,304 次随机、连续左并和连续右并操作；检查每个位置的起止识别、长度和无效位置拒绝，最大实际缓冲 4,096 字节；另外验证了 u32 上界等长度的编解码。没有分配 2^32 字节测试。额外内存是常数个临时标量，不存在每个长 token 一项的 overflow map；底层数组始终恰好 N 字节。完整训练器接入及性能尚未实现。

外部 overflow 哈希表通常也实用，但它仍增加内存；直接扩大到 u16/u32 更不满足“长度表不扩大”的严格要求。内部空位复用有上文 Re-Pair 先例，因此这是本项目可落地的方案，不在这里宣称新算法发现。

**9. 什么结果才足以支持“突破”。**

优先验证一个明确命题：固定相同的预切分、token 单位、频率阈值、同频排序、重叠方向和合并语义，在多种语料与规模下，具体位置索引及紧凑布局是否优于成熟训练器的扫描/搬移方案。

基准至少覆盖中文、英文、多语言/emoji、代码、自然长片段和可控长链/重复片段；单独变化 N、唯一片段比例、K、最大片段长度和线程数。重复同一份数据只增加频率，可能不增加 U，不能拿它证明对物理语料规模的扩展性。记录初始化、合并、导出三个阶段时间，峰值 RSS、位置列表失效率、实际合并次数与内存带宽；分别报告单线程和多线程。

首先与朴素参考实现逐轮比较，再对齐指定主流实现的 merge 序列或最终编码。已有 notebook 中分词器两两 F1 只衡量输出相似程度，既不证明训练语义一致，也不构成性能基准。v1 保存的主要是 token→频率，推理以拼接结果在词表中及频率决定优先级；与保存有序 pair merge rules 的实现存在语义差别，应先明确要保留原算法，还是兼容某个标准模型。

实施顺序建议：先修边界计数并建立参考语义；再做数组初始化、边界写和 bisect 等低成本修正；接入已验证的长度布局，测量加权片段表示的收益；将核心迁入原生代码后做按片段并行；最后才考虑高低频专用队列或更激进的精确批处理。原生实现的优先布局是位图＋跳距；若只想小范围修复 v1 的 255 限制，1 字节端点编码的接入更接近原结构。两者都需同时修改训练及推理里的边界读取与有效性验证。

研究贡献必须比“确定性并行”更具体：YouTokenToMe 连带固定同频规则的压力测试都已有，因此仅提出同一目标不足以构成新颖性。可检验的主张应是，在同样的语义和内存预算下，比已有方案有更低的协调成本、更好的长片段扩展性，或有新的时空界限；也可研究适合自然语言的压缩域 occurrence 更新。是否构成值得发表的系统贡献，取决于完整正确性论证、总内存账本、代表性实验，以及相对这些强先例的具体增量。

对“当年到底贡献了什么”的最稳妥表述是：作者实现了一种紧凑的 Python BPE 训练器，在固定位置表示上直接更新 pair occurrence，并用单字节双端长度减少语料移动和指针开销。这证明了对瓶颈及数据表示的有效判断。现有材料不足以进一步声称：首次提出该算法框架、首次达到该渐近复杂度，或当时已经优于最好的开源训练器。是否存在更窄的、未被本次检索覆盖的原创细节，仍可进一步研究；不能把“未找到完全相同代码”当作原创性的肯定证据。

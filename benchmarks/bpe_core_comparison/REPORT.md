研究对象：efficient_bpe 的表示路线与已有高效 BPE / Re-Pair 核心模块。日期：2026-09-29。

**结论。** 你的双端表示有一个可以量化的特点：利用 token 是原文连续区间这一性质，用长度计算邻居，省掉逐位置的前驱、后继。修正后的 v2 以约 4 字节/位置的语料数组，取得了与 12 字节/位置数组链相近的 Python 训练速度。Prezza 的半字＋位图方案把同一部分进一步压至约 2.1875 字节/位置，但在本次 Python 重写中需要更多解码和位操作，合并阶段耗时约为端点版的 1.8—2.2 倍。三者的单次邻居访问及结构更新都是 O(1)，这里验证的是时空常数的取舍。

这比“都是已有思路”更具体：你的实现选择了较直接的边界访问，已有空间优化工作进一步利用被吞并的槽位存 ID 和跳距，付出更复杂的读取过程。这个实验支持这种设计差异及其工程价值；它不证明新的渐近界或相对所有原生实现的领先。

**比较了哪些代码。** 所有 Python 重写都在同一 CPython 3.12.13 运行，使用 array、整数 ID 和普通 dict。共同驱动负责加权片段、pair→具体位置倒排、频率更新、确定性懒堆和输出。每轮选择最大重叠相邻频数，同频按 pair ID 字典序，实际替换从左向右进行，ID 每轮新建。各后端只改变序列表示。长度上限、前后缀特殊位和原项目的字符串身份规则不在这个统一实验里。

| 实验版本 | 保存的结构 | 与原工作的关系 |
|---|---|---|
| endpoints | 每位置 u32，活跃 token 两端保存 ID，长度在共享表；只写四个端点 | 用户 v2 路线的局部修正版：去掉整段清零，统一了语义与驱动。不是原 v2 原封不动的完整性能。 |
| linked12 | val、prev、next 三个 32 位数组 | 隔离 YouTokenToMe 风格的数组内链；没有移植 RLE 与线程流水线。 |
| linked16 | 再加一个 runlength 数组 | 布局对照，未启用 RLE，所以主结论使用更强的 linked12，而不把它称为完整 YTTM。 |
| bitmap_u32 | u32 文本＋64 位起点位图＋每块 u32 跳距 | 隔离位图跳距本身。 |
| bitmap_halfword | u16 文本＋相同位图/跳距；新 ID 拆成两个 u16，利用被吞并槽位 | 重写 Prezza 的紧凑文本机制；初始 ID 必须小于 65536，后续 ID 支持 u32。 |
| heap / bucket | 普通懒堆 / 扫描高频候选＋低频整数桶 | 单独替换队列，固定相同 pair 顺序；bucket 并非 YTTM 完整训练器。 |

第一轮使用普通模块接口；第二轮把验证、邻居读取和 ID 读取合并成 `inspect_pair`，通过 `merge_known` 复用结果，避免重复解码偏罚位图。下文主表采用第二轮。半字版第二轮还直接构造 u16，消除了第一轮 u32→u16 的临时副本。两轮源码与原始结果都保留。

完整 Prezza 实现还包括全局 TP 位置数组、区间重分组、延迟发现新 pair 和专用队列；这些没有被当前共同驱动替代实验移植。其完整算法的期望线性界不能套到本次 Python 后端。YTTM 的游程压缩和并行同样不在这些训练计时中。[Prezza 原论文](https://arxiv.org/html/1704.08558v1)、[作者文本布局源码](https://github.com/nicolaprezza/Re-Pair/blob/ffb411d8ce9c1232980ec67bee7e678c0b88fd5c/internal/skippable_text.hpp)、[YTTM 源码](https://github.com/VKCOM/YouTokenToMe/blob/f4162d846057a3118222ca04a01b84297eb8a8db/youtokentome/cpp/bpe.cpp)。

**数据与验证。** 只读借鉴了 `/root/code/tokenizers-bpe-benchmark` 的数据和隔离进程方案，没有修改或运行那边的脚本。选定文件已复制到本目录 `data/`，记录内容哈希，不依赖正在更新的文件。来源是 Wikimedia Wikipedia 2023-11-01，固定 revision `b04c8d1ceb2f5cd4588862100d08de323dccfbaa`；原始分片、抽样方法和许可信息见各语言 manifest 及 `reused_benchmark_notes.md`。

真实语料包括英、中、德、日约 1 MiB 样本，另有英中约 4 MiB。统一 Unicode 字符单位，正则 `\w+|[^\w\s]+` 分片，唯一片段加权；另外单测英文按整段切分。训练目标为 3000 条合并规则，min_frequency=2。规模测试使用不去重的随机片段，固定 256 条规则。所有规模均报告物理位置与实际替换数，输入 MiB 不等于训练工作量。

普通驱动在 606 组随机/定向语料、9 种后端上逐轮对照独立的全量重算 oracle；融合驱动又对 204 组语料的 4 种后端和 2 种队列做同样检查。另有边界状态机及大于 65535 的 ID 拆半字验证。性能运行对同一语义检查完整 merge 序列与最终 token 序列的 SHA-256；仅词表大小相等不算通过。

每项在独立子进程运行 3 次，固定随机顺序和 PYTHONHASHSEED，串行执行并绑定 CPU 5。机器为 Xeon Gold 6140 虚拟 CPU 环境；同机有其他任务，主要报告进程 CPU 时间并保留墙钟时间。小幅差异不能视为可靠领先，数据也不能直接外推 Rust/C++；Python 的位操作、方法调用和 heapq 底层 C 实现都会影响常数。

**真实语料：合并阶段 CPU 秒，中位数。** 包括相同的频率、倒排、权重查询和堆工作，不含分片、初始化、最终序列哈希。

**空间：先区分逻辑数组与总进程。** 设 U 为物理位置数，V 为 token 种数，E 为倒排记录数。以下忽略按块取整、数组头和容量余量：

| 表示 | 文本/节点与邻接结构 | 另计 |
|---|---:|---|
| v1 原字符串＋u8 双端长度 | `(s+1)U` 字节，s 是 Python 单个字符串的 1/2/4 字节字符宽度 | pair 字符串、词表、4E 字节位置；token 最长 255 字符 |
| v2 双端 ID | `4U` 字节 | 长度表 O(V)、原 v2 的 8E 字节位置 |
| 本实验 endpoints | `4U` 字节 | 共同驱动采用 4E 字节位置 |
| linked12 | `12U` 字节 | 相同的 4E 字节位置 |
| 半字＋u32 skip | `2U + 12×ceil(U/64)`，约 `2.1875U` 字节 | 相同的 4E 字节位置 |
| 原 Prezza 半字＋u64 skip | 约 `2.25U` 字节 | 全局 TP 约 4U 字节及队列等 |

“12→2”不是全系统比较：2 只含文本槽，完整邻接结构是 2.1875 或 2.25。新 token 的 32 位 ID 存在当前起点及下一个已被吞并的 u16 槽中；位图防止把高/低半字误当成另一个 token。你的 v1 已经省掉了前驱/后继指针；ASCII 时其原文＋边界仅约 2U，但有长度限制和热路径字符串重建成本。

| --- | --- | --- | --- |
| 英文分片 | 36.4 | 37.9 | 35.3 |
| 中文分片 | 77.0 | 79.4 | 76.9 |
| 德文分片 | 43.9 | 46.1 | 43.0 |
| 日文分片 | 70.0 | 72.7 | 69.5 |

在这些样本中，把端点数组进一步压到半字，整体峰值相近，远没有按 4/2.1875 的比例下降。当前 Python 内存优化仍需优先处理哈希表、小容器及位置列表，而不只是边界数组。精确逻辑字节与 Python array 的预留容量分开看：linked 原始记录的 `backend_buffer_bytes` 含预留容量，compact 记录为逻辑长度；上表统一使用结构公式，RSS 表使用进程实测。

**规模与复杂度。** 随机片段的物理输入扩为 4 倍，固定 256 条规则；这里采用第一轮相同接口，所有后端口径一致。

| 输入 | 规则数 | 物理位置 U | 双端 / 秒 | 数组链 / 秒 | 半字 / 秒 |
| --- | --- | --- | --- | --- | --- |
| random-32768 | 256 | 33025 | 0.176 | 0.220 | 0.361 |
| random-131072 | 256 | 132097 | 0.770 | 0.816 | 1.475 |
| random-524288 | 256 | 528385 | 2.933 | 3.041 | 5.677 |
| en-4m | 3000 | 577590 | 3.287 | 3.586 | 6.432 |
| zh-4m | 3000 | 1218853 | 6.102 | 6.171 | 9.090 |

这个规模实验用于检验增长趋势，不能代替证明。用 P 表示最大候选堆规模，R 表示物理替换总次数，G 表示不同词频组数；固定字宽 ID、哈希期望 O(1)、新 ID 不复用及合理失效处理下，共同驱动的保守核心界为 `O(U log(2+P) + R log(2+G))`，R≤U。预处理至少读完 N 个原始字符，物化所有 token 字符串还需按总字符数 D 计费。

| 路线 | 单次邻居/结构更新 | 额外成本 |
|---|---|---|
| v1 双端长度 | O(1) 边界操作 | 每次替换的字符串切片与哈希随 token 长度增长；解除 255 上限后不能继续把它当任意长度下的 O(1)。 |
| 原 v2 | 邻居 O(1)，每次合并清整个 span | 累计 `Σ L_merge`，链式合并可到平方级；频率组数组切片还会把二分表达式变成 O(G) 复制。 |
| 修正 v2 / linked / 位图半字 | 均 O(1) | 共同堆、倒排与权重查询的复杂度相同；更换这些邻接结构只改变常数。 |
| 完整 Re-Pair 系列算法 | 另有期望线性时间方案 | 依赖完整位置组织、队列与摊还证明，不能从单个半字布局直接得到。 |

你相对整词扫描/Vec 搬移实现的优势，是把处理粒度变成具体 occurrence；相对 Re-Pair 和 YTTM 的具体位置更新，它们已经处于同一大方向，区别主要落在表示、队列、重复结构利用和并行协调上。详细条件见 `complexity_notes.md`。

普通 Wiki 样本的初始连续同字符 run 很短，你的固定位置数组在这里具有明确的 payload 优势。对长重复串，一个 run 可以代表上千个字符，YTTM 的压缩节点数量会远小于固定位置数组；这部分收益不能由无 RLE 的重写计时推断或抹去。YTTM 自配对还按 floor(run_length/2) 计分，而共同驱动按重叠相邻数计分，所以若下一步移植完整 RLE，必须先选择兼容语义。

**对当年路线的具体定位。** 可以确认的区别是“用原文跨度隐式表示邻接”，以简单算术和较少的逐位置状态替代显式链接；v2 再把字符串身份换成 ID，避免按 occurrence 反复切片。它在实测中体现为：相对普通数组链，节省结构内存并保留相近速度；相对更激进的半字位图结构，多用部分数组空间、减少解释器中的解码工作。这是有实际意义的设计选择。已有 Re-Pair 工作在更紧凑的全局索引、内存复用和复杂度证明上走得更远，YTTM 在 run 压缩与并行上更完整。现有证据支持这组具体取舍，没有显示你当时跨越了它们已有的渐近复杂度。

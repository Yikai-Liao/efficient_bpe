# BPE：几轮实现演进与精确并行实验

这轮把优化方向做成了代码：减少端点写入、整数 pair key、预筛位置索引、两版位置池、两种紧凑边界，以及广播式和按 pair 所在分片派发的精确并行训练。另外，`ByteSpans` 单独实现了每位置仍为 1 字节的长 token 边界表示。

单进程结果支持三个选择：默认优先整数 pair key；需要省内存时使用预筛索引；稀有 pair 很多、愿意多花 CPU 时考虑位置池 v2。中文样本的整数 key 使总 CPU 时间减少约 12%、RSS 减少约 23%；位置池 v2 则以约 17% 的 CPU 增量换来约 46% 的 RSS 降幅。英文中整数 key 的总 CPU 时间基本持平，位置池没有胜过更简单的预筛版本。

紧凑边界给出了另一种折中：H3 的后端从 4U 降到 3U，但 Python 总 RSS 几乎不变，CPU 增加约 12%–22%；与更省后端空间的 halfword 相比，H3 的总 CPU 时间减少约 26%–42%。因此 H3 值得作为后续原生实现的候选，当前不能据此替换所有 Python 版本。

比较对象是上一轮已修复整段清零、重复边界查询等问题的共同 Python 基线。因此这里的速度变化，是在已经优化过的核心上继续迭代；没有把原版本的二次复杂度缺陷放进分母来放大收益。

## 比较口径

CPython 3.12.13；Xeon Gold 6140；每项新进程，3 次重复取中位数，固定种子打乱执行顺序。单进程计时固定 CPU 5，主表使用进程 CPU 时间；并行允许 6 个 CPU，使用墙钟时间，并另记主进程与所有子进程的整次调用 CPU 时间。系统上可能存在其他任务，因此小幅时间差只能视为观察值。

英文、中文、德文、日文各约 1 MiB，另有英文按段落切分以及英中 4 MiB。真实样本最多训练 3,000 条规则，最低频率为 2；随机串、重复长 run、64 倍权重和合法贪心长链用于边缘情况。权重放大实验同时放大最低频率，保持物理替换工作量不变。数据快照与来源沿用[上一轮](../README.md)。加载、切分、去重和构造 prepared 输入不含在训练时间内；初始化索引含在内；末尾提取与指纹不含在内。并行 `call_total_cpu_seconds` 则覆盖整次调用，包括启动、提取与进程回收。

所有核心采用同一语义：频次含重叠，加权计数；同频选 pair ID 字典序最小者；词内从左到右替换；每条规则分配全新 ID。每个训练进程输出完整规则与最终序列的 SHA-256 指纹，矩阵运行器检查相同输入跨版本一致。小输入另对完全重数频次的 naive oracle 检查。

“每位置多少字节”仅指可变语料后端的逻辑数组长度，不是进程总内存。所有单进程版本仍保留共同的 prepared u32 输入、token 长度表、pair 字典、位置索引、堆和结果规则。RSS 包含解释器、容器头、分配器及初始化峰值；不能用后端数组的节省比例推算 RSS。

整数 key 对中文、日文尤其值得关注，因为 Python tuple 及其持有的整数对象在这些数据上开销明显。它仍然是 Python 大整数对象，不能把一个 key 的真实内存写成固定 8 字节；表中 RSS 才是整体结果。

预筛索引多做一次线性扫描，但避免给不可达最低频率的 pair 建数组。其依据是 fresh ID：旧 pair 的频次只会下降，新出现的边都涉及本轮新 ID。新 pair 必须等本轮累加完成后才能判断是否淘汰；不能按单个 worker 或单次出现的低频提前丢弃。

位置池用每条记录 8 字节的 `(position,next)` 换掉每个 pair 单独的 array 对象，也复用已消费的槽位。原 per-pair 数组的纯 offset 只有 4 字节，所以位置池不保证总是更省、更快。v1 先给所有初始 pair 分配 state，淘汰稀有 pair 后仍保留这些槽；v2 消除了这部分保留。测试中的稀有 pair 定向例子，state 高水位从 100 降为 1，输出不变。堆存 pair key，不存可复用 state 索引，防止旧事件错误命中新状态。

H3/H2.5 是对原端点路线与论文存储思路的结合：初始符号用 u16，合并产生的 u32 ID 放进开头两个槽位；长 token 的长度放进末端空槽，方向 tag 区分起点与终点。它们没有位图邻居搜索，也没有按跨度扫描。H3 多保留一些字节来减少位操作，H2.5 则增加半字节的读改写。结果应与 halfword 同时看，不能只按数组最小选方案。

减少写入在 Python 中未必带来稳定收益：分支、整数运算、字典和堆仍占时间。`LeanEndpoints.inspect_pair` 只接受历史上确实出现过该 pair 的起点，不能作为任意位置的 alive 判定；测试明确保留了超出契约时的假阳性反例。[证明](lean_proof.md)

## 解除 u8 的 255 长度限制

[`ByteSpans`](byte_spans.py) 的唯一逐位置存储是 `bytearray(U)`。短 span 的方向和长度直接写在边界 tag；长度至少 64 时，在头尾各自的内部空槽写入固定 5 个 payload 字节，编码 u32 长度。payload 的最高位恒为 1，与所有边界 tag 分开，旧内部数据不能冒充活起点。先作废被吞并的右起点，再写新边界和 payload。

这保持了每位置 1 字节，并支持 U < 2^32 范围内的长 token；每次只操作固定数量字节。它是边界组件，不包含 token ID，不负责 pair 选择，也没有消除原版字符串切片、哈希和物化词表的成本。对比 H3 的 3U 字节时必须计入 H3 还存储了 ID，不能混为同一内存口径。[布局说明](byte_spans_notes.md)

## 边缘复杂度

定义 U 为去重后实际存储位置数，R 为实际替换次数，K 为规则数，G 为权重分组数，P 为过程中堆的最大规模，P0 为初始候选数。每次替换至少少一个活 token，因此 R = O(U)；每次至多新增两个边事件，历史位置条目累计也为 O(U＋R)。

在固定字长、哈希期望 O(1) 的模型下，这些单进程堆版的核心为

`O(U + (P0 + R) log(2 + P) + R log(2 + G))`，空间为 `O(U + K + P)`。

这不是整个训练管线的无条件最坏界：读取原始数据、字符串去重排序、以及最终词表字符串总长度 D 要另算；恶意哈希碰撞也不在期望哈希模型里。整数编码不允许 ID 截断，位置与 ID 限于 u32；H3/H2.5/halfword 要求初始字母表 ID < 65536，超过时应选 u32 后端。频次保留 Python 整数，已测试大于 2^64 的权重。

权重放大不会增加物理替换次数，也不会引入按频次数值范围扫描的桶；若把任意精度整数的位数也当成变量，Python 的算术和比较还需计入相应位复杂度，不能对无限大权重宣称单位时间。

这些实现均不会因 token 变长而逐次清理整段内部空间。位置池的链回收按实际条目计费，每条条目的遍历/回收次数受其创建次数约束；每轮不会全表重建。预筛版本的额外全扫描只发生在初始化。

## 并行：原始端点布局可以保留

串行依赖在全局贪心规则选择上。端点数组本身不要求所有合并都由同一线程执行：只要完整 piece 是不可跨越的边界，就可让每个分片独占其语料、位置索引和局部计数。主进程选择一条全局规则，各分片替换并返回频次变化，主进程归并后再选择下一条。这保持词内替换次序与全局同频规则。

第一版 [`parallel_driver.py`](parallel_driver.py) 每轮向所有 worker 广播，并等待全部结果。第二版 [`parallel_sparse_driver.py`](parallel_sparse_driver.py) 维护 pair 的历史 owner 位掩码，只通知可能包含该 pair 的分片；掩码可以包含已失效 owner，但不能漏掉 owner。初始 owner 来自各片计数，新 owner 来自本轮新增边。闲置 worker 在下次收到任务时补齐缺少的 token 长度，累计补齐量 O(KW)，W 为 worker 数。

两版都训练同一份全局词表。`serial1` 顺序执行同一套 worker/delta 算法，用来观察分片算法本身的开销；`spawn1/2/4` 是广播版，`sparse2/4` 是 owner 版，`packed` 是直接单进程训练器。worker 用 `spawn`，所有进程共享完整可用 CPU affinity；没有误把它们限制到单个 CPU。

按整次训练墙钟时间的三次中位数看，四 worker 的结果取决于输入：英文段落从单进程 `packed` 的 6.924 秒降到广播 `spawn4` 的 4.843 秒、owner `sparse4` 的 5.058 秒；英文 4 MiB 则是 2.886 秒对 2.912/2.936 秒，三次原始范围重叠，不能称为提速；中文 4 MiB 的广播版中位数为 5.008 秒，对比 5.170 秒基线，范围也重叠，而 owner 版为 5.485 秒。owner 中位数在三种真实输入上都比广播版慢约 0.8%、9.5%、4.5%；英文 4 MiB 与段落数据的三次范围仍重叠，中文 4 MiB 的范围未重叠，但只有三次观测。它确实减少了 IPC：四 worker 英文 4 MiB 约从 24,012 降至 18,692 条消息，中文约从 24,012 降至 21,214 条；但计算哪些 owner 需要工作、维护 owner 目录及分片不均衡仍有开销，减少消息本身不能保证降墙钟时间。并行版总 CPU 时间也高于 `packed`，如中文 4 MiB 的 `spawn4/sparse4` 中位数约 10.04/10.44 秒，对比 5.95 秒；这代表用更多 CPU 与内存换取部分输入上的低延迟，不是普遍效率提升。单进程 `spawn1` 在真实数据上均慢于 `packed`，显示进程启动与分片协议本身的成本。

独立 PSS 采样每个配置只运行一次，不参与上表三次性能中位数。它记录的英文 4 MiB 峰值 PSS 为 `packed/spawn4/sparse4` 的 66.3/110.9/112.8 MiB，中文 4 MiB 为 161.1/251.6/254.2 MiB，英文段落为 75.4/163.9/164.9 MiB。采样间隔约 20 ms，可能漏掉短峰；这里只说明并行进程树的内存代价量级。

父进程 CPU 降低不代表提速；这里只以墙钟时间判断并行速度。JSON 还保留各进程的 `ru_maxrss`，但不能相加后当成真实物理内存峰值：它们不是同时刻峰值，也不扣共享页，且历史资源统计跨 exec 保留。实际出现了所有 worker 峰值都与父进程相同、但 worker 当前 RSS 明显更低的情况。[Linux getrusage 文档](https://man7.org/linux/man-pages/man2/getrusage.2.html)

因此另开独立的内存剖析进程，以约 20 ms 间隔读取整个被测进程树的 `smaps_rollup` 并相加 PSS，包含主进程、worker 和 multiprocessing resource tracker，排除采样器。PSS 按比例分摊共享页。这些结果各测一次，属于采样峰值，可能漏掉短暂尖峰；受采样器影响的运行不纳入前面的性能中位数。指纹仍与未采样运行一致。

每条规则的理想耗时仍至少包含 `max(各片本轮工作量)＋归并＋同步`。广播版控制消息为 2KW；owner 版为两倍各轮历史 owner 数之和。后期规则频次低，序列化、唤醒和屏障可能占主导；owner 目录本身也消耗时间和内存，减消息不保证提速。分片初始按字符数平衡，并不保证每条规则的命中也平衡。

按词分片还有明确边界：单个超长 piece 只能落在一个 worker；实验中即使请求四个 worker，也会实际只创建一个。若要把同一长 piece 切开，边界可能产生合并、改变邻接和频次，必须设计跨片边界协议，不能独立训练后拼词表。

原生多线程的下一步应保留分片所有权，让各片直接访问自己的数组区间和局部索引，用共享的只读 token 长度表与稀疏 delta 缓冲替代每轮 pickle。所有分片的语料后端总大小约为 4(U＋W−1)，不是每个 worker 都复制整个 U；当前 Python 原型另外保留原始输入和局部输入副本，解释器与字典也有成本。共享压缩元数据时还必须按物理字节或位图 word 定义所有权：H2.5 读取分隔符所在字节，也可能与邻片写同字节的另一半冲突；bitmap 更可能由两片写同一 u64。每片独立元数据或正确对齐可避开这些竞争。

这里没有实现任意多条规则并行发布。YouTokenToMe 的两轮流水线值得借鉴，但在本实验固定 lex 同频规则下，提前发布下一条规则还必须证明未完成的 delta 和新 pair 不会胜出；仅检查两个被选 pair 不重叠是不够的。[YTTM 固定版本源码](https://github.com/VKCOM/YouTokenToMe/blob/f4162d846057a3118222ca04a01b84297eb8a8db/youtokentome/cpp/bpe.cpp)

## 与论文的关系

这些实现借鉴的是可分开验证的存储与维护思路。2016 年的 Space-Efficient Re-Pair 用空槽支持常数时间跳过空白，并用同步与摊销控制位置维护；2017 年的 Practical and Effective Re-Pair 提供了 halfword 文本、位图/跳距与集中位置存储的实践依据。[2016 论文](https://arxiv.org/html/1611.01479v1)；[2017 论文](https://arxiv.org/html/1704.08558v1)

本轮位置池是显式 `(position,next)` 链，不是论文的 TP 区间重排与完整延迟发现算法；队列仍是 Python 堆。因此不能将论文的整体线性时间或空间定理直接赋予本实验。H3、字节 span、整数 key 与 owner 派发属于这轮组合和工程验证；当前结果也没有建立它们的学术优先权。
